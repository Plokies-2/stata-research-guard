# Reading Paper Workflows

For substantial Stata authoring or restructuring, learn from an actual connected research workflow before deciding the implementation. This is a reading and reasoning obligation, not a prescribed code structure or an automatic check. Command syntax may already be settled and this reading may still change the design.

## Choose a useful source, not a canonical answer

Start from the current research problem: what data and sample feed which estimates and outputs, and what implementation choice needs improvement? Consider a direct documented-command approach before treating a paper's manual implementation as the starting point. Inspect plausible original-code alternatives for that question. Prefer a source whose relevant flow you can understand and whose technique addresses the current problem; explain the choice briefly. A familiar or bundled package can be the best fit, but its presence here, journal prestige, downloads, or code frequency do not establish that. Look beyond the existing collection when its examples are indirect, awkward, incomplete, or mismatched. Do not force a new search merely to replace a source that already fits and has been critically read.

One well-chosen connected workflow can suffice. A second source is useful when it offers a concrete competing technique or resolves a gap; no fixed paper quota, exhaustive survey, best-paper ranking, or permanent winner is needed. Different stages can benefit from different papers. A maintainer guide can explain an implementation choice, but it does not replace the actual paper workflow reading requested here.

## Follow the code through the result

Read the README or available entry instructions and the active entrypoint to understand the overall project and which branches produce the relevant results. Then follow the original source through inputs, transformations and sample construction, estimation, stored/returned results, and the final table or figure. Read shared definitions, callbacks, and upstream/downstream files when they affect that path. A master file, filename list, command occurrence, search hit, or this document alone is insufficient.

"Whole workflow" means the connected analysis needed to understand the current work, not every unrelated outcome, appendix, bundled ado, or dataset in a repository. Follow substantive dependencies to their source rather than cutting fixed-size windows. If a specification differs between branches, read the difference. When the task changes several distinct paths, cover those paths rather than using one convenient regression as a proxy for all of them. Read available raw logs and artifacts when useful; never run a paper just to supply missing logs.

While reading, reason about where the observation unit or sample changes; whether the estimator and specification remain visible; why a loop, callback, intermediate dataset, or file boundary exists; and how statistical results reach their consumers without unnecessary reconstruction. These are prompts for inquiry, not boxes to fill. Add other questions when the research needs them and omit irrelevant ones.

Try to complete the work through documented automation: bulk syntax, options, returned results, stored estimates, and native postestimation/export facilities. Read the selected command's relevant help and consider another suitable documented command before concluding that manual work is necessary. A paper's hand-written calculations, coefficient/SE/star assembly, or statistical-row reconstruction may reflect older tools or special output needs. Investigate alternatives while a concrete implementation question remains; stop when a supported approach satisfies the current research and output requirements. If something remains unsupported, name that gap and implement only it. A narrow permutation callback or required workbook layout can be appropriate; do not remove it merely because it is custom code. This principle does not eliminate necessary source-data transformations or research definitions such as treatment timing and sample construction. Judge the reduction in indirection and redundant statistical work, not the language used or lines deleted.

## Make the comparison actionable

Explain in ordinary prose, with original file/section locations, what the paper does, why the technique helps or does not help the current source, and the smallest useful change or reason to retain the current code. A short comparison near the implementation discussion is sufficient; do not generate an audit form or an obligatory standalone report. Do not merely say the code "matches a top journal".

Keep current user choices, material sample/specification/output contracts, and official/maintainer command semantics authoritative. A paper's locals, manual interactions, estimator wrappers, TeX exports, output-specific files, or old software conventions are not permissions to overwrite those choices. Equally, do not reject a necessary callback or research-specific operation simply because a preferred example lacks it. A paper may contain mistakes; recognize and decline them without claiming a full replication or causal assessment.

The writing model reads the sources itself. Give the existing peer the sources and current work so it can independently challenge the choice and the resulting implementation. Reuse this reading in the existing post-change review; do not add producer/auditor/reauditor stages. Keep judgments in model reasoning and concise prose. Do not implement Python or other-language validators, regex checks, expected-output oracles, ratings, or code-shape gates for this obligation.

## Obtain only the material needed

Use accessible original package files already present, including the selected full-file snapshots in this plugin's `data/source_archive/index.json` (relative to the plugin root). Resolve the original path to `archive_path` and actually open the `.source` file: it contains original text, not a workflow summary. The index is navigation, not proof of reading or a list of recommended winners. Some papers have only individual files bundled, so trace missing dependencies in the original package before calling the path understood.

Otherwise use the authors' or journal's replication repository and retain the source URL/DOI, version, and original paths. Fetch only necessary code and documentation; do not collect datasets or full archives when individual code files suffice. Follow the user's browser and login instructions when authenticated access is needed; never embed account-specific details in this public skill. Another suitable accessible paper is preferable to pretending an unavailable source was read. If no suitable connected source is available, disclose that limitation and continue independent work without claiming that the required reading or final workflow comparison occurred. Do not create a server gate or silently substitute a synthetic example.

## Concrete starting points, open to replacement

These are navigation examples, not a syllabus or default source selection. Read the originals and choose according to the current problem.

- **Vulnerability and Clientelism**, AER 2022: [article](https://www.aeaweb.org/articles?id=10.1257/aer.20190565), [package V1](https://doi.org/10.3886/E173341V1). The existing archive index contains all six `corpus/packages/173341/dofiles/` files. `0. Master.do` connects cleaning, variable construction, separate electoral-data preparation, and main/appendix analyses. For the household Table 2 path, follow `1. Cleaning.do` treatment and retained survey sample, `2. Variable_Construction.do` household selection and index construction through its final household save, then `4. Main_Tables.do` Table 2 estimation and export. The visible outcome loop and distinct research panels are informative; its manual table helpers, TeX details, and manual interaction construction elsewhere are not a style standard. The entrypoint states the outputs; consult the original README for additional package-access context when needed.
- **Social Media and Mental Health**, AER 2022: [article](https://www.aeaweb.org/articles?id=10.1257/aer.20211218), [package V1](https://doi.org/10.3886/E175582V1). Follow `Code/Master_file.do`, path definitions, the data-preparation and analysis masters, `Data_Prep_ACHA_1.do` and `Data_Prep_ACHA_2.do`, then main-text tables/figures. This exposes how treatment timing and sample construction reach different specifications. The bundle contains the full `Code/Analysis/Figures_MainText/Figures_MainText.do`, but not the complete preparation/main-table path: retrieve missing files if choosing it. Read the README's restricted-data limits; code reading does not establish execution. The explicit specification blocks are useful comparisons, while wrappers and output choices remain open to criticism.

[Julian Reif's Stata Coding Guide](https://julianreif.com/guide/) and [Social Science Data Editors' code guidance](https://social-science-data-editors.github.io/new-guidance/Guidance/Requested_information_code.html) can help with entrypoints, data/output separation, and documentation of execution. Read only the relevant parts. Their recommendations are not this project's rules: do not import a submission checklist, expected-result assertions, a library design, or a preferred output format wholesale.
