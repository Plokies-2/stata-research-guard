# General Rules

For research authoring or a material interface change, read once from this file or a current complete Guard response. Reuse while visible and unchanged; reread after context loss or a relevant rule change. The workflow entrypoint handles interface-preserving edits without loading this full document. If a Guard call is needed, its complete-rules delivery and explicit visible-hash reuse contract still apply.

## Research purpose

- Make the researcher's ability to follow the analysis in execution order the highest implementation priority. Use longer commands with continuation lines, named intermediate values, or separate visible specification blocks when they make the research choices easier to read. Judge the effort it takes to follow the executed path. Give line counts, character counts, and line savings no weight as measures of readability.
- The user and project determine estimand, treatment, merge keys, sample, controls, FE, weights, VCE, event axis, model role, outputs, required checks, and workflow order. Where implementation is unspecified, choose a direct, researcher-readable approach that fulfills those requirements without omitting them or treating extra procedures as mandatory. Resolve routine gaps from context; ask only when an unresolved choice materially changes the research or authorized scope.
- Respect the user's stated research and inference choices. Make additional analytical choices explicit and explain why they fit the current question. Interpret observed paths, uncertainty and appropriate comparisons in context; do not impose an unrequested mechanical candidate-acceptance rule or substitute statistical thresholds for researcher judgment.
- Protect source inputs and submitted or designated comparison baselines at the file level. Read original files in place and write new data, estimates, or exports to a separate path when the baseline must be retained. Use `replace` only at an authorized output destination. Use saved artifacts to preserve and compare earlier results. Remove superseded code paths from the active analysis and report substantive discrepancies when a comparison is requested. Preserve the specified units, required call order, and output contracts.
- When a change affects how a maintained table, figure, or dataset is produced or used, start with that output and check what its actual consumer reads. Trace the affected path to the saved result, sample, observation unit, or source transformation as needed. Compare the output's meaning and structure with the request and the existing artifact. Follow the active code when deciding whether intermediate work is needed.
- Follow the live path from source observations and stored results to their consumers. Before discarding unmatched rows or replacing returned state, read what would be lost. When several outputs consume the same estimate, restore its results rather than estimating it again. Judge the whole replacement, including names, temporary state, mappings, and save/reload steps the reader must follow: a shorter block may only move work elsewhere. Keep names aligned with what values mean at each stage; do not repurpose a substantive variable as unrelated scratch storage merely to share code. Retain intermediate datasets, callbacks and explicit repetition when they make the research objects easier to understand.

## Direct analysis

When an implementation choice remains unclear, consult only the relevant comparison in [code-examples.md](code-examples.md). Each illustration states its assumptions, the concrete reading difficulty, and when the alternative would not fit; it does not prescribe the current project's research choices.

- Write comments about the current code: the data or variables used, the operation, and the research reason or a consequential assumption. Do not write private work-history comments such as "agreed changes", "September 11 meeting", "updated on [date]", "professor's advice", or chat/approval/author records. Translate a relevant decision into its substantive rationale: use "Fix region at its 2019 value to avoid post-treatment reclassification", not "Use 2019 region as agreed at the meeting". Dates that define data, events, policy or sample periods, and necessary source citations remain appropriate. When editing an affected block, replace history comments with a concise current explanation or remove them if they add no explanation; preserve research logic and source-paper excerpts. Keep requested change history in Git or project documentation, outside analysis-code comments.
- Before adding a mode, argument, or branch to a maintained `.do`, inspect the actual input datasets or saved estimates, output destinations, and the callers or consumers of both flows. Keep one maintained file per coherent research work unit. Extend the existing file when a variant shares its workflow and contributes to the same maintained analysis. Put related variants in visible sections or shallow loops. Give an independent analysis or established stage with its own input-to-output flow a purpose-named file, even when it shares a panel, estimator, or project folder. See [workflow-taxonomy.md](workflow-taxonomy.md).
- For a bounded change, read the affected estimation and output blocks, apply the requested edit and change only its direct dependencies. Retain adequate preparation, storage and export code. Removing an option calls for removing it in the existing command and rerunning the affected estimates, not rebuilding the analysis. A display-only change can reuse suitable stored estimates. Readability, native-interface and workflow-organization guidance does not authorize expanding a local edit into a refactor; a requested refactor still belongs in the original work-unit file.
- Create a new maintained `.do` for an independent workflow, a required external interface, a demonstrated restart boundary, or an explicitly requested separate file. A changed option, outcome, table, or chat request alone is insufficient. Edit the existing producer for an in-place change. Avoid competing `_v2`, `_new`, `_rerun`, option-named scripts and a thin original that forwards to a duplicate. If the source is read-only and a change is authorized elsewhere, use one working copy with the necessary edits. When output replacement is authorized, retain established destinations. Report which producer changed and which outputs ran.
- Delete superseded and unused code in the affected workflow once direct callers and output consumers confirm it is obsolete. Remove unused modes, commented-out alternatives, helpers, and arguments with their obsolete references in the same edit. Use the existing work area for one-off exploration. Before finishing, integrate only code needed to reproduce maintained analyses or required deliverables, and delete the rest of the scratch code created for the task. Do not keep abandoned experiments as runnable branches or archive copies of disposable scripts. Preserve source inputs, submitted baselines, required reproducers, active checkpoints, requested artifacts and research records regardless of the direction or significance of the results.
- Before writing code or adding settings, check whether the active tool's defaults, native capabilities and supported options meet the research and output requirements. Use them where sufficient: do not restate defaults with redundant explicit options or reproduce supported behavior through manual calculations, duplicated implementations or wrappers. Preserve explicit user choices and required project or template settings. For a remaining gap, identify the relevant native bulk syntax, factor/time-series operators, postestimation, storage or export interface. Reuse visible evidence; read only the relevant official/maintainer help needed to resolve uncertainty about defaults, inputs, sample, returned-state lifetime or downstream use. Investigate another suitable command only while a concrete gap remains. Use a suitable interface without obscuring the research meaning, and implement only the unsupported remainder. Do not replace a suitable native command with a manual algorithm merely to avoid a small justified interface.
- Keep persistent-variable creation, definition and label together; preserve imported source labels unless the user asks to change them. Verify merge keys and retained states; do not use `merge m:m`, force-drop duplicates, or conceal a material failure behind a dependency probe.
- Show consequential choices where the work happens. Keep input datasets, merge keys, sample restrictions, and formulas visible at the data step or in its immediate setup. Keep the actual estimator, outcome, treatment or event terms, sample, controls, FE, weights, and VCE visible at estimation. Put the relevant save or export close to its producer, or show which saved result the downstream code reads. Avoid wrappers, numbered specifications, and distant macros that make the reader reconstruct these choices.
- Inspect existing helpers and macros as well as proposed ones. In a readability refactor, their presence in old code is not a reason to keep them; retain an interface only when an actual external caller or user requirement needs it. Verify the active entrypoint before treating a missing file or empty folder as permission to invent a replacement analysis.
- In research refactoring, repetition, DRY, fewer lines, and centralized output handling do not justify a new `program`, ado, estimator/exporter wrapper, generic helper, specification registry, mode, dispatcher, positional `word` parsing, or speculative branch. A reusable interface needs an explicit user request or a pre-existing project contract. A documented native command may require a small callback for the requested statistic; keep that callback narrow and the analysis specification visible rather than replacing the command with a hand-written algorithm.
- Prefer native bulk syntax or one flat loop for genuinely mechanical repetition. Keep a short outcome or other iteration list directly in the loop header, with the estimator/graph command and consequential options visible in its body; the iterator is necessary control state, not a forbidden convenience alias. Do not duplicate the same estimation, summary, storage and export block for each outcome merely to avoid a loop, or because an optional basic-syntax help lookup failed. Similar appearance alone does not justify combining substantively different transformations or plotting requirements. Keep explicit blocks when combining them would require the reader to decode labels, numbering, or distinct research choices. A second loop is useful only for two mechanical axes, such as sample and outcome; never add a third. Write different research specifications as visible blocks rather than encoding them in strings, catalogs, counters, or nested branches. Keep genuine exceptions beside the affected command.
- For a hypothesis with several requested mechanical comparisons, prepare their outcome, reporting-unit, sample and specification variants together and run a coherent batch before interpreting the comparisons. Reuse shared preparation and unchanged stored estimates. Do not default to one small fit followed by a new report and another small fit; do not expand a bounded request into an unrequested combination search. Keep research specifications visible under the shallow-loop rule rather than adding a generic dispatcher or specification registry.
- Keep short outcome/control lists and ordinary option blocks visible in the analysis command or its immediately surrounding loop. Do not make a reader leave that block to decode a top-of-file `global`, convenience `local`, or nested list alias. House rule: inline a simple path, variable-list composition, specification or option bundle referenced at only one code site; one reference inside a loop is still one site. Replacing a one-use `global` with a `local`, or merely moving its definition, does not remove the unnecessary indirection. Apply this within the authorized block and its direct dependencies, not as a reason for project-wide cleanup.
- Repeated references alone do not justify a macro for a short list. Retain a shared definition when it is an actual user configuration point, an existing external interface, or a substantial common list whose analysis/output consumers benefit from staying consistent; keep it easy to find near the relevant work. Shared project roots, necessary loop iterators, temporary-file handles, meaningful derived variables and immediately consumed returned results can remain. Judge their purpose and the reader's work rather than imposing a variable-count threshold, duplicating whole analyses to avoid loops, or converting `global` to `local` by default.
- Keep analysis at the top level wherever possible and indent only real scopes. Do not nest block conditionals inside another conditional or add a mode branch around nested loops. Use a data filter for sample selection, a guard such as `continue` for a local skip, and visible blocks for distinct specifications. Keep the two-loop limit for mechanical repetition. Use continuation lines only for a continued command. Keep meaningful key, missingness, range, and sample checks close to the step they verify.
- When a project actually has distinct work units, a short master may call their existing broad stages: integrated preparation/panel, descriptives, regression with its outputs, and requested robustness. These are possible roles, not required files. Use sections within the work-unit file and apply the new-file boundary above; keep a small analysis together.
- Preserve adequate existing names. New or approved renamed modules use workflow-role names such as `cleaning_data.do`, `summary.do`, `regression.do`, and `robustness.do`; update direct calls and documentation together. Role names do not imply creating every file.

## Evidence and outputs

- Before a project's first research run, ask once about an Excel codebook if no codebook, designated workbook or prior decision is available. Continue authorized work independent of the decision. Follow [codebook.md](codebook.md) for creation, maintenance and formatting.
- Keep generated files and paths purposeful and easy to navigate. Inspect the affected code's save/export destinations and actual generated files, not just its declared outputs. Distinguish deliverables, reusable analysis data and needed logs from one-use intermediates; a file being generated or read by the current code does not by itself justify permanent storage. Use `tempfile` for transient Stata datasets and export assembly; keep other temporary work in the project's existing `work`, `tmp`, `cache`, or `build` area. Retain an intermediate file when an actual downstream consumer, costly restart, or user requirement needs it. Use clear, consistent names and the existing project layout; avoid scattered paths, duplicate formats and unnecessary versioned folders. Within the authorized scope, remove newly unnecessary temporary files and update affected consumers when changing paths. Preserve source data, baselines and required execution records. Review these choices during readability checks and inspect the resulting files after execution; do not create a separate inventory or automatic quality gate.
- Choose commands yourself. Official help governs official grammar; maintainer help governs user-written commands. Paper code and logs are nonbinding context, not templates or grammar authority. Preserve the current project's sample and specification when adapting an example. When evidence informs code you write or revise, name the help topic, paper or project source you actually used and the choice it informed in the final reply.
- Follow `command-evidence.md` for lookup and reuse. Skip Guard for read-only work, comments/formatting, literal interface-preserving changes, verbatim relocation, and unchanged-file execution without a semantic issue. For material interfaces, use exact-command help; discovery and expanded command documentation/examples address unresolved command questions. Stop only the branch whose material grammar is unavailable.
- Follow the workflow's [evidence guidance](../SKILL.md#use-the-evidence-that-resolves-the-implementation). Use [paper-workflow-reading.md](paper-workflow-reading.md) when a paper can inform an unresolved implementation choice or the user requests a paper comparison.
- Choose a command for the required estimand, sample, inference and output before considering installation. A suitable built-in command remains a candidate even outside the dictionary. When the selected package is missing, use the current user request or an applicable prior approval and follow host approval controls. For an authorized installation, install only the needed package and required dependencies from SSC or the official maintainer into the user's main Stata installation's normal shared ado location, separately from analysis code. When approval is needed, request it for that installation and continue unaffected work. Do not change the estimator or inference merely to avoid installation; reconsider the choice only when another documented interface better fits the research. Do not add `which`, `capture which`, `findfile`, `ado dir`, or `confirm command` package probes or undocumented fallback implementations.
- Keep each reported quantity and data-dependent table or figure note tied to the result that produced it: its model or group, effective observations, weighting and definition. Shared input data, the same outcome, or equal observation counts do not establish that a quantity can be reused. Compute sample-dependent summaries while the intended sample and returned state are available, then consume or retain them with the corresponding result through a documented interface. A common descriptive statistic may be shared when that is the requested meaning and its population is clear; model-specific quantities may be shared only when their relevant inputs and definitions coincide. Preserve the requested sample policy rather than forcing a common sample to simplify reporting. Use the result-ownership comparison in [code-examples.md](code-examples.md) when this handoff is unclear.
- Save reusable estimates as `.ster`; restore them for downstream tables and figures instead of re-estimating. Keep naming and replace/append order tied to visible model blocks or loop axes. Preserve native raw `e(b)` names and required actual omitted/base rows through stored estimates, tables, and event-study selectors; do not manually generate interactions or reconstruct statistical rows.
- Assemble a large batch's result workbook after its coherent comparison set is ready, unless an interim output is needed for a concrete decision. A small addition does not by itself justify repeatedly rebuilding every worksheet, preview and export. Reuse completed results, update only the affected outputs when practical, and separate estimation failures from collection, formatting and process-exit failures. For broad exploration, read compact coefficient, uncertainty, warning and support tables first; render informative or unresolved comparisons as needed for path interpretation or the user's requested presentation. Preserve unfavorable results and honor requests for complete figures.
- Use Excel tables, PDF figures, and `.ster` estimates unless the user specifies otherwise. Choose a documented table/export interface that fits the research purpose and requested output while preserving results and inference. Use the interface's native features, whether provided by built-in commands or a user-written exporter. Read its relevant options before assembling coefficient/SE rows by hand; use its supported statistics, additional rows, titles and notes. Confirm that the result being exported is the intended effect, not an intermediate regression, and preserve coefficient identity, effect-specific samples and nonstandard inference. An auxiliary layout step need not replace the statistical table. Required multi-sheet layout may use a small post-export formatter; do not reconstruct statistics or create a second statistical source.
- For new outputs, use Malgun Gothic (맑은 고딕) for Korean text where available. Use plain Excel formatting with white/no-fill cells, black text, restrained bold headings, and only necessary borders. Follow the user's template. In a narrow edit, retain existing font and other styling outside the requested change.
- When designing or redesigning a figure, use a wide plotting area and prefer a centered legend below the axes for multiple series. Wrap long legends or share one across panels when it helps. Follow the user's template and inspect the export at its intended display size for usable width and clipping. Preserve requested scales, event positions, and confidence intervals.
- Show control-variable coefficients and their standard errors as ordinary body rows when the intended model returns them. Do not hide them with `keep()`/`drop()` or replace them with a footer saying "Controls: Yes" merely to shorten the table. Preserve actual omitted/base rows and distinguish a control absent from a specification from one included but omitted in estimation. When the estimator does not return reportable control coefficients for the intended result, use a concise per-model `Controls` footer identifying the controls actually specified; this is a display fallback, not evidence that the controls were all retained. Check available code, returned results and log warnings, and disclose known exclusions. Do not fabricate coefficients, borrow nuisance-regression coefficients, or rerun a different estimator to fill these rows. Determine availability from the actual estimator results rather than assuming it from the command name.
- When the user names an existing Excel workbook or a preferred workflow such as their Dropbox tables, open the actual reference workbook before designing worksheet exports; reading its producer code alone is insufficient. Compare it with the current workbook when available. In the export task instructions, name the reference workbook and relevant sheets and state the intended sheet grouping, outcome/sample/specification column headers and order, coefficient rows with parenthesized standard errors and stars, applicable footer statistics/notes, and relevant display conventions. Include this concrete structure in any delegated export or review request; "Excel output" or "outreg2 format" alone is insufficient. Use the reference's researcher-facing structure with the current project's actual models and inference, not its coefficients, number of specifications, or inapplicable statistics. Preserve the table generated by `outreg2` through temporary assembly and Excel export rather than substituting a long-form results dataset. Make only necessary display adaptations and inspect the saved workbook against the requested structure. State the structure briefly in the task/update; do not create a separate template, inventory, or validation system. If the reference is unavailable, disclose that limitation rather than claiming a match.
- Read actual code and results yourself. Judge tables and figures in their intended research context, not as standalone explanations. Keep only labels needed to distinguish variables, specifications, axes/units, statistics and groups; familiar short labels are enough. Keep definitions and full methods in the surrounding text or README, adding a brief note only to prevent a concrete misreading. Avoid duplicate titles and oversized text; follow a suitable existing project style. More annotation or matching coefficients does not establish clarity or causal validity.
- For a display-only edit, preserve unrequested axes, event positions, CI caps, marker/series order, opacity, font sizes and legend settings. Inspect the actual affected export at its intended display size; an option value or an unchanged coefficient table does not show that opacity is perceptible or that CIs and legends are readable. Fix the observed display issue with the relevant native option. Pixel identity and fixed clearance distances are not default acceptance requirements for every small edit.
- Distinguish the input group count from the estimation sample and each effect's contributing groups or switchers. Read the actual returned state and warnings before interpreting a candidate; explain when a broad input group only supports one treatment-change direction. Check the source definitions of treatment and outcome coding before interpreting a numeric category change as a substantive change. Choose further comparisons through research judgment, not an automatic minimum-group or IN/OUT-ratio gate.
- Do not create semantic validators, graders, classifiers, rankings, expected-answer oracles, audit queues, promotion states, result-fact layers, or hidden fallbacks. In particular, do not require a previous run's exact number of successful or unidentified fits, return-code distribution, or coefficient/significance pattern as a condition for collecting or exporting new results. Preserve actual failures and unavailable statistics instead. Meaningful key, range and sample assertions, requested baseline comparisons and direct exported-cell readback remain useful checks of concrete errors; they do not certify research validity. Keep provenance as source paths/citations and needed metadata; use researcher judgment for interpretation.
