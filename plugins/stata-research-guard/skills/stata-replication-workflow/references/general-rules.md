# General Rules

Read once for the relevant task, from this file or a current complete Guard response. Reuse while visible and unchanged; reread after context loss or a relevant rule change.

## Research purpose

- Prioritize code the researcher can comfortably read, inspect, and modify over shorter code. Before changing a meaningful research block, understand its purpose and identify a concrete difficulty in following or using it. Choose a change that resolves that difficulty while keeping the data, sample, and calculations clear. An optimization request permits retaining adequate code; repetition or an opportunity to shorten a name does not by itself justify a rewrite. This judgment does not require a checklist, extra comments, or a planning artifact.
- The user and project determine estimand, treatment, merge keys, sample, controls, FE, weights, VCE, event axis, model role, and outputs. Resolve routine gaps from context; ask only when an unresolved choice materially changes the research or authorized scope.
- Preserve source inputs, submitted baselines, units, call order, and requested output contracts. An existing implementation or reference may contain mistakes; do not silently change research choices or propagate a discovered error into project instructions.
- When designing or restructuring a workflow, read affected outputs backward as well as following data forward: from the requested table, figure, or reusable dataset to the statistic/estimate, effective sample, observation unit, and source transformations that supply it. Use existing artifacts and the user's requirements; no new mockup or planning document is required. Work backward from the meaning and structure of the output, never from desired coefficient values, signs, significance, or a preferred conclusion. Reconcile this reading with the actual forward code before removing intermediate work.
- Follow the live path from source observations and stored results to their consumers. Before discarding unmatched rows or replacing returned state, read what would be lost. When several outputs consume the same estimate, restore its results rather than estimating it again. Judge the whole replacement, including names, temporary state, mappings, and save/reload steps the reader must follow: a shorter block may only move work elsewhere. Keep names aligned with what values mean at each stage; do not repurpose a substantive variable as unrelated scratch storage merely to share code. Retain intermediate datasets, callbacks and explicit repetition when they make the research objects easier to understand.

## Direct analysis

- Keep one maintained `.do` per research work unit so the researcher knows which file to open and change. A work unit is a coherent research task or established stage with its own purpose and input/output flow, not each chat request, run, option, outcome, specification, table or figure. Find its existing producer and continue there. Edit and refactor that same file in place; do not create `_v2`, `_new`, `_rerun`, option-named scripts, or a thin original that merely calls a newly rewritten duplicate. Put related variants and outputs in visible sections or existing shallow loops.
- For a bounded change, read the affected estimation and output blocks, apply the requested edit and change only its direct dependencies. Retain adequate preparation, storage and export code. Removing an option calls for removing it in the existing command and rerunning the affected estimates, not rebuilding the analysis. A display-only change can reuse suitable stored estimates. Readability, native-interface and workflow-organization guidance does not authorize expanding a local edit into a refactor; a requested refactor still belongs in the original work-unit file.
- A new `.do` needs a genuinely independent research task/stage, a required external interface, a demonstrated restart boundary that sections and saved data/estimates cannot reasonably serve, or the user's explicit request for a separate file. Explain that concrete reason before creating it; file length, parallel agents, a fresh session, or a changed specification is not a reason. Otherwise continue in the existing file without asking for approval. Preserve comparison artifacts or version history rather than keeping competing active scripts. If the source must remain read-only, use one working copy with only the necessary edits and continue in that copy. When output replacement is authorized, retain established destinations; add only the missing comparison layer to existing exports/plots. Report the producer used, changes and outputs actually rerun without a new checklist or validator.
- Before reproducing a manual operation, identify the specific supported option or returned-result interface that could perform it: native bulk syntax, factor/time-series operators, postestimation, storage, or export. Use the relevant official/maintainer help section to check its inputs, sample, returned-state lifetime, and downstream use. Reuse visible evidence; investigate another suitable command only while a concrete gap remains. Use the interface when it meets the research and output requirements without obscuring their meaning, and implement only the unsupported remainder. Do not replace a suitable native command with a manual algorithm merely to avoid a small justified interface.
- Keep the estimator and consequential outcome, treatment/event terms, sample, controls, FE, weights, and VCE visible where estimation runs. A `run_model, outcome() controls() absorb() weight() cluster()` call hides the estimator even when its arguments are visible.
- Inspect existing helpers and macros as well as proposed ones. In a readability refactor, their presence in old code is not a reason to keep them; retain an interface only when an actual external caller or user requirement needs it. Verify the active entrypoint before treating a missing file or empty folder as permission to invent a replacement analysis.
- In research refactoring, repetition, DRY, fewer lines, and centralized output handling do not justify a new `program`, ado, estimator/exporter wrapper, generic helper, specification registry, mode, dispatcher, positional `word` parsing, or speculative branch. A reusable interface needs an explicit user request or a pre-existing project contract. A documented native command may require a small callback for the requested statistic; keep that callback narrow and the analysis specification visible rather than replacing the command with a hand-written algorithm.
- Use native bulk syntax or a flat loop when it makes a genuinely shared operation easier to follow. For example, figures that share a plotting/export procedure and formatting can use one flat loop when only the outcome, sample, or destination changes; keep the graph command and shared options visible in the loop. Similar appearance alone does not justify combining figures with different substantive transformations or plotting requirements. Keep explicit blocks when combining them would require the reader to decode labels, numbering, or distinct research choices. A second loop is useful only for two mechanical axes, such as sample and outcome; never add a third. Write different research specifications as visible blocks rather than encoding them in strings, catalogs, counters, or nested branches. Keep genuine exceptions beside the affected command.
- House rule: do not introduce `local` macros by default, or convert existing `global` macros to `local` merely to narrow scope. Use literals for one-use bindings and keep genuine shared path/variable groups close to their use; do not hide a one-use regression specification in macros.
- Keep a `local` when the actual command interface or research flow needs it, such as a loop iterator, a temporary-file handle, or an immediately consumed returned result whose replacement would complicate the code. Do not force such necessary locals into globals or manual code just to satisfy the house rule. This narrow exception does not authorize convenience aliases, option bundles, or routine global-to-local refactoring.
- Keep top-level code unindented, indent only real scopes, and use continuation lines only for a continued command. Avoid decorative nesting, unnecessary counters, and branches for already established data state. Meaningful key, missingness, range, and sample assertions are useful; do not add generic defensive scaffolding.
- When a project actually has distinct work units, a short master may call their existing broad stages: integrated preparation/panel, descriptives, regression with its outputs, and requested robustness. These are possible roles, not required files. Use sections within the work-unit file and apply the new-file boundary above; keep a small analysis together.
- Preserve adequate existing names. New or approved renamed modules use workflow-role names such as `cleaning_data.do`, `summary.do`, `regression.do`, and `robustness.do`; update direct calls and documentation together. Role names do not imply creating every file.

## Evidence and outputs

- Whenever coding creates or changes data variables, including renaming, recoding, converting units/types, deriving, aggregating, or removing variables, create or update the project's Excel codebook as part of the work, regardless of language or implementation method. Use the user-designated workbook as the format reference; the `FnGuide_variable_list_Nayeon.xlsx` style is a simple worksheet grouped by variable topic with five columns in this order: `varname`, `Item`, `Item Name`, `format / unit`, `note`. Record the actual variable name, source item code when available, readable definition, format/unit/category coding, and relevant source, derivation formula, missing-value treatment or usage notes. For derived variables without a source item code, leave `Item` blank rather than inventing one. Explain renames, removals and consequential definition changes in `note`; make the applicable dataset/stage clear when a name has different meanings across stages. Base entries on the actual code and available data/source documentation, and identify unresolved definitions instead of guessing. Update an existing codebook in place rather than creating one per run or script; preserve a user-required existing layout. Keep it in the project's established documentation location, with readable Korean text, bold column/group headings and widths suited to the five fields. Before completion, read back the affected entries against the implemented variable changes and available execution evidence; distinguish intended changes from unexecuted code. This is researcher documentation, not an automatic variable inventory, semantic validator, or approval gate.
- Keep generated files and paths purposeful and easy to navigate. Inspect the affected code's save/export destinations and actual generated files, not just its declared outputs. Distinguish deliverables, reusable analysis data and needed logs from one-use intermediates; a file being generated or read by the current code does not by itself justify permanent storage. Use `tempfile` for transient Stata datasets and export assembly; keep other temporary work in the project's existing `work`, `tmp`, `cache`, or `build` area. Retain an intermediate file when an actual downstream consumer, costly restart, or user requirement needs it. Use clear, consistent names and the existing project layout; avoid scattered paths, duplicate formats and unnecessary versioned folders. Within the authorized scope, remove newly unnecessary temporary files and update affected consumers when changing paths. Preserve source data, baselines and required execution records. Review these choices during readability checks and inspect the resulting files after execution; do not create a separate inventory or automatic quality gate.
- Choose commands yourself. Official help governs official grammar; maintainer help governs user-written commands. Paper code and logs are nonbinding context, not templates or grammar authority. Preserve the current project's sample and specification when adapting an example.
- Follow `command-evidence.md` for lookup and reuse. Skip Guard for read-only work, comments/formatting, literal interface-preserving changes, verbatim relocation, and unchanged-file execution without a semantic issue. For material interfaces, use exact-command help; discovery and expanded command documentation/examples address unresolved command questions. Stop only the branch whose material grammar is unavailable.
- Follow the workflow's required connected-paper reading for substantial authoring or restructuring; command-help sufficiency does not waive it. `paper-workflow-reading.md` explains how to select and critically interpret a source without treating it as a template or code-quality certificate.
- Choose a command for the required estimand, sample, inference and output before considering installation. A suitable built-in command remains a candidate even outside the dictionary. If the chosen package is missing, install it on demand in the user's main Stata installation's normal shared ado location, separately from analysis code; do not create an isolated ado environment. Installing and enabling this plugin authorizes on-demand installation and use of its supported user-written commands and their required dependencies from SSC or official maintainer sources, unless the user restricts this scope. Do not preinstall the catalog or ask again for this covered setup. This standing authorization does not override host approval controls. Do not change the estimator or inference merely to avoid installation; reconsider the choice only when another documented interface better fits the research. Do not add `which`, `capture which`, `findfile`, `ado dir`, or `confirm command` package probes or undocumented fallback implementations.
- Save reusable estimates as `.ster`; restore them for downstream tables and figures instead of re-estimating. Keep naming and replace/append order tied to visible model blocks or loop axes. Preserve native raw `e(b)` names and required actual omitted/base rows through stored estimates, tables, and event-study selectors; do not manually generate interactions or reconstruct statistical rows.
- Use Excel tables, PDF figures, and `.ster` estimates unless the user specifies otherwise. Prefer `outreg2` first for researcher-facing tables, including special DID results, whenever it preserves the requested results and inference. Read its relevant options before assembling coefficient/SE rows by hand; use its supported statistics, additional rows, titles and notes. Confirm that the result being exported is the intended effect, not an intermediate regression, and preserve coefficient identity, effect-specific samples and nonstandard inference. Use another interface only for a concrete unmet requirement; an auxiliary layout step need not replace the statistical table. Required multi-sheet layout may use a small post-export formatter; do not reconstruct statistics or create a second statistical source.
- For outputs containing Korean text, explicitly set the default font to Malgun Gothic (맑은 고딕), unless the user or required template specifies another font. Apply it through the relevant graph or document/table formatting settings.
- Show control-variable coefficients and their standard errors as ordinary body rows when the intended model returns them. Do not hide them with `keep()`/`drop()` or replace them with a footer saying "Controls: Yes" merely to shorten the table. Preserve actual omitted/base rows and distinguish a control absent from a specification from one included but omitted in estimation. When the estimator does not return reportable control coefficients for the intended result, use a concise per-model `Controls` footer identifying the controls actually specified; this is a display fallback, not evidence that the controls were all retained. Check available code, returned results and log warnings, and disclose known exclusions. Do not fabricate coefficients, borrow nuisance-regression coefficients, or rerun a different estimator to fill these rows. Determine availability from the actual estimator results rather than assuming it from the command name.
- When the user names an existing Excel workbook or a preferred workflow such as their Dropbox tables, open the actual reference workbook before designing worksheet exports; reading its producer code alone is insufficient. Compare it with the current workbook when available. In the export task instructions, name the reference workbook and relevant sheets and state the intended sheet grouping, outcome/sample/specification column headers and order, coefficient rows with parenthesized standard errors and stars, applicable footer statistics/notes, and relevant display conventions. Include this concrete structure in any delegated export or review request; "Excel output" or "outreg2 format" alone is insufficient. Use the reference's researcher-facing structure with the current project's actual models and inference, not its coefficients, number of specifications, or inapplicable statistics. Preserve the table generated by `outreg2` through temporary assembly and Excel export rather than substituting a long-form results dataset. Make only necessary display adaptations and inspect the saved workbook against the requested structure. State the structure briefly in the task/update; do not create a separate template, inventory, or validation system. If the reference is unavailable, disclose that limitation rather than claiming a match.
- Read actual code and results yourself. Judge tables and figures in their intended research context, not as standalone explanations. Keep only labels needed to distinguish variables, specifications, axes/units, statistics and groups; familiar short labels are enough. Keep definitions and full methods in the surrounding text or README, adding a brief note only to prevent a concrete misreading. Avoid duplicate titles and oversized text; follow a suitable existing project style. More annotation or matching coefficients does not establish clarity or causal validity.
- Do not create semantic validators, graders, classifiers, rankings, expected-answer oracles, audit queues, promotion states, result-fact layers, or hidden fallbacks. Keep provenance as source paths/citations and needed metadata; use researcher judgment for interpretation.
