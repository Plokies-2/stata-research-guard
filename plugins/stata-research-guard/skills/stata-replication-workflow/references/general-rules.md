# General Rules

Read these rules once for the relevant Stata task, from this file or a complete current Guard response. Revisit affected sections if scope or rules change. For a refactor, compare the source and proposed call sites directly.

## Research judgment and evidence

- The user and project, not Guard, determine estimand, sample, treatment, merge key, controls, FE, weights, VCE, event axis, model role, and outputs. Resolve a material gap from current context or ask.
- Choose the command yourself. Official documentation governs official commands and maintainer documentation governs user-written commands; do not invent undocumented syntax. Paper code is contextual, never grammar authority or a template.
- Skip Guard for read-only review or explanation, comment or formatting-only edits, literal path or label changes that leave the command interface unchanged, verbatim relocation, and unchanged-file execution with no semantic issue. For material code, data changes or saves, estimation or tests, exports, or consequential returned-state use, obtain exact-command Phase 2 evidence. Use Phase 1 only when the command is unclear; otherwise call Phase 2 directly. Stop only a branch whose material syntax remains unavailable.
- Request evidence only for interfaces that matter. The command index is a discovery aid, not a closed boundary. Reuse a visible packet only while the command, version, material options, returned interface, and downstream use remain unchanged.

## Research refactoring contract

- Refactoring means making the path from data and sample to estimator, specification, stored estimate, and output easier to follow. It does not mean minimizing lines, eliminating all repetition, maximizing reuse, or applying DRY as an end in itself. Never present line-count reduction as evidence of better research code.
- Preserve explicit repetition when removing it would hide a research choice. First try the command's native bulk or append interface, then a flat loop, then a mechanical two-axis loop. Keep real exceptions beside the affected command.
- In an existing research-analysis refactor, do not introduce a new `program`, ado, estimator wrapper, exporter wrapper, generic helper, or option-heavy interface unless the user explicitly requests that reusable interface or an existing project contract already requires it. Repeated calls alone never justify one.
- Judge the resulting call site, not the helper definition. A call such as `run_model, outcome() treatment() controls() absorb() weight() cluster()` is parameter plumbing that hides the estimator even though its arguments are visible. If a proposed change replaces a visible estimator loop with such calls, keep the loop.

## Direct Stata

- Write shallow, direct code whose sample, specification, and output are visible at use. Do not add registries, modes, dispatchers, positional `word` parsing, future interfaces, wrappers, or speculative branches merely to retain an analysis, robustness check, placebo, permutation, or export.
- Use literals for one-use bindings. At each core estimation, write outcome, treatment or event terms, consequential `if` or `in`, controls, FE, weights, and VCE at the call site. Locals are only for iterators, temporary or scratch values, immediately consumed `r()` or `e()` results, or lexical state of an approved program; globals only for a shared root or real cross-file contract.
- Add a `program` only for an explicitly requested reusable command interface or a pre-existing project contract, not for repetition, fewer lines, deduplication, or centralized output handling. Use a `.do` module for a durable stage that needs no interface. Keep top-level code unindented and indent once per real scope; use loop depth two only for genuine mechanical axes and never depth three.
- Name new `.do` modules, and modules renamed within an approved structural refactor, for workflow roles rather than project-specific outcomes, periods, or thresholds: prefer `cleaning_data.do`, `summary.do`, `regression.do`, `robustness.do`, `permutation.do`, or `placebo.do`, not names such as `main_early_reaction_share10.do`. Do not retroactively rename existing files; within the user's approved scope, change the related master calls, call sites, and documentation together.
- Do not multiply `if` or conditional branches for outcome-specific exceptions, missingness, counters, or checks already supplied by established data state. Keep a branch only for a real specification or data difference. Do not test package availability with `which`, `capture which`, `findfile`, `ado dir`, or `confirm command`, or add throwaway file-existence or cleanup checks. If a Guard-selected official or maintainer command fails at runtime because it is not installed, do not mix installation into estimation or regression code and do not substitute or reimplement it. In a separate step, use official or maintainer installation guidance, install only what is needed within the user's authority, restart Stata, and run the original command.
- Preserve native factor-variable syntax and raw `e(b)` names through tables, event-study selectors, stored estimates, and formatters, including required estimated rows and actual omitted or base raw rows in their required order. Do not manually create interactions or reconstruct coefficients, standard errors, omitted or base rows, or their ordering.
- Use the documented command's own options, factor-variable, wildcard, range, bulk, returned-state, append or replace, and export support before manual code. Add only the concrete missing transformation, after the native command when practical. Reduce identical boilerplate with the shallowest readable construct, never at the cost of hidden specification, parameter plumbing, or deeper control flow.

## Outputs and review

- Preserve requested paths, call order, labels, samples, specifications, row or sheet order, tables, figures, estimates, and output contracts unless the user requests a change. Master files retain exact comma-separated `* Project Inputs:` and `* Project Outputs:` inventories and a role sentence before each `.do` call.
- Use Excel for tables, PDF for figures, and `.ster` for reusable estimates; do not create TeX. Derive `.ster` names and stable `replace` then `append` order from visible loop axes when practical, and restore estimates downstream instead of rerunning models. Keep one-sheet `outreg2` as direct `.xls` export with `nor2` and approved `addstat`. For required multi-sheet workbooks, let `outreg2` produce its native coefficients, standard errors, significance markers, headers, and notes; a small formatter may assemble sheets and add unsupported layout, but must not reconstruct statistics or merge a parallel sidecar. Consult the exporter guide before duplicating default output.
- Verify by reading code and observed runtime state, logs, tables, figures, estimates, and artifacts. Keep static observations, runtime completion, and substantive or causal validity distinct. Do not create semantic validators, graders, rankers, classifiers, expected-answer oracles, audit queues, promotion states, or hidden fallbacks.
