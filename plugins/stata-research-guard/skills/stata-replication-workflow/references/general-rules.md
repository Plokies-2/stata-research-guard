# General Rules

Read these rules once per session from a complete Guard response or this file, and reread them only after context loss (through Guard, send `include_rules: true`). Interface-preserving edits do not need this document.

## Research purpose

- Readability of the executed path comes first (see SKILL.md). Use longer commands with continuation lines, named intermediate values, or separate visible specification blocks when they make the research choices easier to follow; line and character counts carry no weight.
- The user and project determine estimand, treatment, merge keys, sample, controls, FE, weights, VCE, event axis, model role, outputs, required checks, and workflow order. Where implementation is unspecified, choose a direct, researcher-readable approach that fulfills those requirements without omitting them or treating extra procedures as mandatory. Resolve routine gaps from context; ask only when an unresolved choice materially changes the research or authorized scope.
- Respect the user's stated research and inference choices. Make additional analytical choices explicit and explain why they fit the current question. Interpret observed paths, uncertainty and comparisons in context; do not impose an unrequested mechanical acceptance rule or substitute statistical thresholds for researcher judgment.
- Protect source inputs and submitted or designated comparison baselines at the file level. Read original files in place, write new data, estimates, or exports to a separate path when the baseline must be retained, and use `replace` only at an authorized output destination. Compare with saved artifacts, report substantive discrepancies when a comparison is requested, and preserve the specified units, call order, and output contracts.
- When a change affects a maintained table, figure, or dataset, start from what its actual consumer reads and trace back through stored results, sample, observation unit and source transformations as far as needed. Before dropping unmatched rows or replacing returned state, read what would be lost. Restore an estimate that several outputs share instead of estimating it again. Judge a replacement as a whole, including names, temporary state, mappings and save/reload steps: a shorter block may only move work elsewhere. Keep names true to what values mean at each stage, do not repurpose a substantive variable as scratch storage, and keep intermediate datasets, callbacks or explicit repetition that make the research objects easier to understand.

## Direct analysis

When an implementation choice remains unclear, consult only the relevant comparison in [code-examples.md](code-examples.md); its illustrations do not prescribe the current project's research choices.

- Comments describe the current code: the data or variables used, the operation, and the research reason or a consequential assumption. Do not write work-history comments (meetings, approvals, "updated on [date]", advisor or chat records); translate a relevant decision into its rationale, e.g. "Fix region at its 2019 value to avoid post-treatment reclassification". Dates that define data, events, policy or sample periods, necessary source citations and source-paper excerpts stay. When editing a block, replace its history comments with a concise current explanation or remove them; requested change history belongs in Git or project documentation.
- Keep one maintained `.do` per coherent research work unit. Before adding a mode, argument, or branch, inspect the actual inputs or saved estimates, output destinations, and the callers or consumers of both flows. Extend the existing file when a variant shares its workflow, using visible sections or shallow loops. Give an independent analysis or stage with its own input-to-output flow a purpose-named file, even when it shares a panel, estimator, or folder. Create a new file only for that, a required external interface, a demonstrated restart boundary, or an explicit request; a changed option, outcome, table, or chat request is not enough. Avoid competing `_v2`, `_new`, `_rerun` or option-named scripts and thin originals that forward to a duplicate. For a read-only source with authorized changes, use one working copy; when output replacement is authorized, keep established destinations. Report which producer changed and which outputs ran. See [workflow-taxonomy.md](workflow-taxonomy.md) for stage roles and a short master; preserve adequate names and update direct calls and documentation with an approved rename.
- For a bounded change, read the affected estimation and output blocks, apply the requested edit and change only its direct dependencies; keep adequate preparation, storage and export code. Removing an option means removing it from the existing command and rerunning the affected estimates; a display-only change can reuse suitable stored estimates. Readability and organization guidance does not turn a local edit into a refactor, and a requested refactor stays in the original work-unit file.
- Delete superseded and unused code in the affected workflow once direct callers and output consumers confirm it is obsolete, including unused modes, commented-out alternatives, helpers, arguments and their references. Use the existing work area for one-off exploration; before finishing, integrate only code needed for maintained analyses or required deliverables and delete the remaining scratch code created for the task, without archive copies or runnable abandoned branches. Preserve source inputs, baselines, required reproducers, active checkpoints, requested artifacts and research records, whatever the direction or significance of the results.
- Before writing code or adding settings, check whether the active tool's defaults, native capabilities and supported options meet the requirements. Use them where sufficient: do not restate defaults or reproduce supported behavior through manual calculations, duplicate implementations or wrappers. Preserve explicit user choices and required project or template settings. For a remaining gap, look for native bulk syntax, factor/time-series operators, postestimation, storage or export interfaces, reusing visible evidence and reading only the help needed to resolve defaults, inputs, sample, returned-state lifetime or downstream use. Implement only the unsupported remainder, keeping the research meaning visible. A documented command may need a small callback for the requested statistic; do not replace it with a hand-written algorithm.
- Keep persistent-variable creation, definition and label together; preserve imported source labels unless asked. Verify merge keys and retained states; do not use `merge m:m`, force-drop duplicates, or conceal a material failure behind a dependency probe.
- Show consequential choices where the work happens: input datasets, merge keys, sample restrictions and formulas at the data step; the estimator, outcome, treatment or event terms, sample, controls, FE, weights and VCE at estimation. Put the save or export near its producer, or show which saved result downstream code reads.
- Do not add a new `program`, ado, estimator/exporter wrapper, generic helper, specification registry, mode, dispatcher, positional `word` parsing, numbered specification, or speculative branch for repetition, DRY or fewer lines; a reusable interface needs an explicit user request or a pre-existing project contract. In a readability refactor, existing helpers and macros get the same scrutiny: keep one only for an actual external caller or user requirement. Verify the active entrypoint before treating a missing file or empty folder as permission to invent a replacement analysis.
- Mechanical repetition: use native bulk syntax or one flat loop over the group's global (`foreach y of global financial`) with the command and consequential options visible in its body; the iterator is necessary state, not an alias. Add a second loop only for a second mechanical axis (e.g. sample × outcome), never a third. Do not copy the same estimation, storage and export block per outcome to avoid a loop, including after a failed optional basic-syntax lookup. Similar appearance alone does not justify combining substantively different work. Write distinct research specifications as visible blocks, not strings, catalogs, counters or nested branches, and keep genuine exceptions beside the affected command.
- Globals for outcome groups (house rule): give each group of outcome variables, and similar variable lists that the do-file loops over, summarizes or tabulates, one `global` named for what it holds, in a short noun a reader remembers: `$employment`, `$pay`, `$financial`, `$board`. Seeing `$financial` should tell the reader it holds Tobin's Q, ROA and ROE without scrolling up. Define these globals together in one block at the top of the do-file, or in the master when several do-files use them, and build larger groups from smaller ones (`global labor "$employment $pay"`) instead of retyping members. Then loop over or list the global wherever that group is estimated, summarized, plotted or tabulated. Write each list once, wrapped with `///` as needed; list length alone does not justify a branch, and membership is never looked up with `if`/`strpos()`.
- Keep what a command does inside the command. The arguments that build the model and the output stay written where they run: regressors and controls, `absorb()` fixed effects, weights, `vce()`, sample conditions, `keep()`/`drop()`/`order()` coefficient selection, `relocate()` positions, axis, label and scale options. A reader looking at `reghdfe` or `coefplot` must see the specification and the exported range there, even when the same options repeat across several commands. Do not move them into globals, and do not hide a sample condition inside a variable-list global. Project root and data paths stay globals.
- Locals stay for what only lives inside a block: loop iterators, values computed per iteration, tempfile and tempname handles, and returned results kept across a command that overwrites them. Compute a derived value such as a stripped outcome name once per iteration and reuse it. Do not copy a global into a local, rename a group under a second name, or give groups numbered, generic or display-driven names (`outcomes1`, `vars`, `event_axis_vars_emp_n`). Apply this within the authorized block and its direct dependencies, not as project-wide cleanup.
- Do not use `quietly` (or `qui`), as a prefix or around a block: estimation, summaries and checks should print in the log so the researcher can read what ran. Use an option such as `meanonly` when a command offers one.
- Indent only real scopes: no block conditional nested inside another and no mode branch around loops. Use a data filter for sample selection, `continue` for a local skip, and `if` for conditions that define the sample or depend on data or execution state. Use continuation lines only for a continued command, and keep the `///` markers of one command in a single column. Align them with `node hooks/stata-align.cjs <file.do> --lines <edited ranges>` from the plugin root instead of padding by hand; it changes only the spaces before `///` and leaves other commands as they are. Keep key, missingness, range and sample checks close to the step they verify.
- For a hypothesis with several requested mechanical comparisons, prepare their outcome, reporting-unit, sample and specification variants together and run a coherent batch before interpreting them, reusing shared preparation and unchanged stored estimates. Build the result workbook once that set is ready unless an interim output is needed for a concrete decision; a small addition does not justify rebuilding every worksheet, so update only affected outputs when practical. Do not alternate small fits and new reports, and do not expand a bounded request into an unrequested combination search. Separate estimation failures from collection, formatting and process-exit failures. For broad exploration, read compact coefficient, uncertainty, warning and support tables first and render comparisons as interpretation or presentation requires. Preserve unfavorable results and honor requests for complete figures.

## Evidence and outputs

- Before a project's first research run, follow the codebook question in SKILL.md and [codebook.md](codebook.md).
- Keep generated files and paths purposeful. Inspect the affected code's actual save/export destinations and generated files, and distinguish deliverables, reusable analysis data and needed logs from one-use intermediates: being generated or read does not justify permanent storage. Use `tempfile` for transient Stata datasets and export assembly and the project's existing `work`, `tmp`, `cache` or `build` area for other temporary work. Keep an intermediate file only for an actual downstream consumer, costly restart, or user requirement. Use clear names and the existing layout, without scattered paths, duplicate formats or versioned folders. Within scope, remove newly unnecessary temporary files and update consumers when paths change. Inspect the resulting files after execution.
- Choose commands yourself. Paper code and logs are nonbinding context, not templates or grammar authority; preserve the current project's sample and specification when adapting an example. For lookup, exemptions and grammar authority, follow [command-evidence.md](command-evidence.md); stop only the branch whose material grammar is unavailable. Use [paper-workflow-reading.md](paper-workflow-reading.md) when a paper can inform an unresolved implementation choice or a comparison is requested.
- Choose a command for the required estimand, sample, inference and output before considering installation; a suitable built-in command remains a candidate outside the dictionary. Install a missing package only under the current request or an applicable prior approval and the host's approval controls: only the needed package and dependencies, from SSC or the official maintainer, into the main Stata installation's normal shared ado location, separately from analysis code. When approval is needed, request it and continue unaffected work. Do not change the estimator or inference to avoid installation. Do not add `which`, `capture which`, `findfile`, `ado dir` or `confirm command` probes or undocumented fallback implementations.
- Tie each reported quantity and data-dependent note to the result that produced it: its model or group, effective observations, weighting and definition. Shared input data, outcome or equal observation counts do not establish reuse. Compute sample-dependent summaries while the intended sample and returned state are available and carry them with their result through a documented interface. Share a descriptive statistic only when that is the requested meaning and its population is clear, and a model-specific quantity only when its inputs and definitions coincide. Preserve the requested sample policy rather than forcing a common sample. See the result-ownership comparison in [code-examples.md](code-examples.md).
- Use Excel tables, PDF figures, and `.ster` estimates unless the user specifies otherwise. Save reusable estimates as `.ster` and restore them for downstream tables and figures instead of re-estimating, with naming and replace/append order tied to visible model blocks or loop axes. Preserve native raw `e(b)` names and actual omitted/base rows through stored estimates, tables, and event-study selectors.
- Plan for Stata's name limits before writing the loop: an `estimates store` name has at most 27 characters (Stata creates `_est_name`), and a local name at most 31. Store each model under the outcome name itself, without a prefix such as `m_`. When an outcome name is longer than 27 characters, save the model to a `.ster` file named for the outcome, and at the consumer load it with `estimates use` and plot the active result (`coefplot .`). Do not build macro names from outcome names (`` local id_`outcome' ``) or strip prefixes in each loop to make names fit.
- Choose a documented table/export interface that fits the requested output and use its native statistics, additional rows, titles and notes before assembling coefficient/SE rows by hand. Confirm the exported result is the intended effect, not an intermediate regression, and preserve coefficient identity, effect-specific samples and nonstandard inference. A required multi-sheet layout may use a small post-export formatter; never reconstruct statistics, generate interactions by hand, or create a second statistical source.
- For new outputs, use Malgun Gothic (맑은 고딕) for Korean text where available, plain Excel formatting (white/no-fill cells, black text, restrained bold headings, only necessary borders), and the user's template. In a narrow edit, keep existing styling outside the requested change.
- Show control-variable coefficients and standard errors as ordinary body rows when the intended model returns them; do not hide them with `keep()`/`drop()` or a "Controls: Yes" footer merely to shorten the table. Preserve actual omitted/base rows and distinguish a control absent from a specification from one omitted in estimation. When the estimator returns no reportable control coefficients, use a concise per-model `Controls` footer naming the controls specified; it does not show they were retained, so check code, returned results and warnings and disclose known exclusions. Determine availability from the actual results, never fabricate or borrow coefficients, and do not rerun a different estimator to fill these rows.
- When the user names a reference workbook or preferred workflow such as their Dropbox tables, open the actual workbook before designing worksheet exports; its producer code alone is insufficient. In the task instructions, including any delegated export or review request, name the workbook and sheets and state the sheet grouping, outcome/sample/specification headers and order, coefficient rows with parenthesized standard errors and stars, footer statistics/notes and display conventions; "Excel output" or "outreg2 format" alone is insufficient. Follow its researcher-facing structure with the current project's models and inference, not its coefficients, number of specifications or inapplicable statistics. When the reference is produced by `outreg2`, keep the `outreg2` table through temporary assembly and Excel export rather than substituting a long-form results dataset. Inspect the saved workbook against the requested structure; if the reference is unavailable, say so rather than claiming a match.
- For figures, follow the user's template; descriptive figures and tables also follow [descriptive-outputs.md](descriptive-outputs.md). When designing one, use a wide plot area and, for several series, a centered legend below the axes, wrapped or shared across panels as needed. In a display-only edit, preserve unrequested scales, axes, event positions, CIs and caps, series order, opacity, font sizes and legend settings. Inspect the actual export at its intended display size, since option values or an unchanged coefficient table do not show readability, and fix observed issues with the relevant native option; pixel identity and fixed clearances are not default acceptance tests.
- Read actual code and results yourself and judge tables and figures in their research context. Keep only labels needed to distinguish variables, specifications, axes/units, statistics and groups; leave definitions and methods to the surrounding text or README, adding a brief note only to prevent a concrete misreading. Avoid duplicate titles and oversized text. More annotation or matching coefficients does not establish clarity or causal validity.
- Distinguish the input group count from the estimation sample and each effect's contributing groups or switchers. Read the returned state and warnings before interpreting a candidate, explain when a broad input group supports only one treatment-change direction, and check the source coding of treatment and outcome before reading a numeric category change as substantive. Choose further comparisons by research judgment, not an automatic minimum-group or IN/OUT-ratio gate.
- Do not create semantic validators, graders, classifiers, rankings, expected-answer oracles, audit queues, promotion states, result-fact layers, templates, inventories, quality gates or hidden fallbacks. Do not require a previous run's number of successful fits, return codes or coefficient/significance pattern as a condition for collecting or exporting new results; preserve actual failures and unavailable statistics. Key, range and sample assertions, requested baseline comparisons and exported-cell readback remain useful checks of concrete errors, not certificates of validity. Keep provenance as source paths, citations and needed metadata.
