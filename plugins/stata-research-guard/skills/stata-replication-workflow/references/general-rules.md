# General Rules

Read once for the relevant task, from this file or a current complete Guard response. Reuse while visible and unchanged; reread after context loss or a relevant rule change.

## Research purpose

- Keep the path from source data and sample to estimator, specification, stored estimate, and output easy to read. Refactoring reduces indirection, not necessarily lines. Some explicit repetition is clearer than a new interface.
- The user and project determine estimand, treatment, merge keys, sample, controls, FE, weights, VCE, event axis, model role, and outputs. Resolve routine gaps from context; ask only when an unresolved choice materially changes the research or authorized scope.
- Preserve source inputs, submitted baselines, units, call order, and requested output contracts. An existing implementation or reference may contain mistakes; do not silently change research choices or propagate a discovered error into project instructions.

## Direct analysis

- Use the documented command's native options, factor variables, time-series operators, wildcard/range/bulk syntax, returned results, and append/export capabilities before manual code. Implement only a concrete remaining requirement. Do not replace a suitable native command with a manual algorithm merely to avoid a small justified interface.
- Keep the estimator and consequential outcome, treatment/event terms, sample, controls, FE, weights, and VCE visible where estimation runs. A `run_model, outcome() controls() absorb() weight() cluster()` call hides the estimator even when its arguments are visible.
- Inspect existing helpers and macros as well as proposed ones. In a readability refactor, their presence in old code is not a reason to keep them; retain an interface only when an actual external caller or user requirement needs it. Verify the active entrypoint before treating a missing file or empty folder as permission to invent a replacement analysis.
- In research refactoring, repetition, DRY, fewer lines, and centralized output handling do not justify a new `program`, ado, estimator/exporter wrapper, generic helper, specification registry, mode, dispatcher, positional `word` parsing, or speculative branch. A reusable interface needs an explicit user request or a pre-existing project contract. A documented native command may require a small callback for the requested statistic; keep that callback narrow and the analysis specification visible rather than replacing the command with a hand-written algorithm.
- Try native bulk syntax, then a flat loop. A second loop is useful only for two mechanical axes, such as sample and outcome; never add a third. Write different research specifications as visible blocks rather than encoding them in strings, catalogs, counters, or nested branches. Keep genuine exceptions beside the affected command.
- House rule: do not introduce `local` macros by default, or convert existing `global` macros to `local` merely to narrow scope. Use literals for one-use bindings and keep genuine shared path/variable groups close to their use; do not hide a one-use regression specification in macros.
- Keep a `local` when the actual command interface or research flow needs it, such as a loop iterator, a temporary-file handle, or an immediately consumed returned result whose replacement would complicate the code. Do not force such necessary locals into globals or manual code just to satisfy the house rule. This narrow exception does not authorize convenience aliases, option bundles, or routine global-to-local refactoring.
- Keep top-level code unindented, indent only real scopes, and use continuation lines only for a continued command. Avoid decorative nesting, unnecessary counters, and branches for already established data state. Meaningful key, missingness, range, and sample assertions are useful; do not add generic defensive scaffolding.
- Prefer a short master and at most the needed broad stages: integrated preparation/panel, descriptives and basic figures, regression and its estimates/tables/figures, requested robustness. Use sections within these files. Do not split by command, outcome, specification, table, or graph. Extra files need a concrete independent input, interface, or costly restart purpose. Keep a small analysis together.
- Preserve adequate existing names. New or approved renamed modules use workflow-role names such as `cleaning_data.do`, `summary.do`, `regression.do`, and `robustness.do`; update direct calls and documentation together. Role names do not imply creating every file.

## Evidence and outputs

- Choose commands yourself. Official help governs official grammar; maintainer help governs user-written commands. Paper code and logs are nonbinding context, not templates or grammar authority. Preserve the current project's sample and specification when adapting an example.
- Follow `command-evidence.md` for lookup and reuse. Skip Guard for read-only work, comments/formatting, literal interface-preserving changes, verbatim relocation, and unchanged-file execution without a semantic issue. For material interfaces, use exact-command help; discovery and expanded documentation/paper blocks are only for unresolved questions. Stop only the branch whose material grammar is unavailable.
- If a selected package is actually missing, install it separately from analysis code using official/maintainer guidance within the user's authority, then use the original command. Do not add `which`, `capture which`, `findfile`, `ado dir`, or `confirm command` package probes or undocumented fallback implementations.
- Save reusable estimates as `.ster`; restore them for downstream tables and figures instead of re-estimating. Keep naming and replace/append order tied to visible model blocks or loop axes. Preserve native raw `e(b)` names and required actual omitted/base rows through stored estimates, tables, and event-study selectors; do not manually generate interactions or reconstruct statistical rows.
- Use Excel tables, PDF figures, and `.ster` estimates unless the user specifies otherwise. Let the exporter produce coefficients, SEs, stars, statistics, and notes it supports. Required multi-sheet layout may use a small post-export formatter; do not reconstruct statistics or create a second statistical source. Read exporter help before duplicating defaults.
- For outputs containing Korean text, explicitly set the default font to Malgun Gothic (맑은 고딕), unless the user or required template specifies another font. Apply it through the relevant graph or document/table formatting settings.
- The workflow invokes a fresh peer before refactoring and after substantive code changes. Give it actual source and artifacts so it can name concrete corrections, then address those findings. Read actual code, data, logs, estimates, tables, and figures yourself. A zero return code or unchanged coefficients alone does not establish readability or causal validity.
- Do not create semantic validators, graders, classifiers, rankings, expected-answer oracles, audit queues, promotion states, result-fact layers, or hidden fallbacks. Keep provenance as source paths/citations and needed metadata; use researcher judgment for interpretation.
