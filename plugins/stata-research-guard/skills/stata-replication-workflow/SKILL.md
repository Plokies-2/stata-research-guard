# Stata Research Workflow

Use the `stataResearchGuard` MCP server as the evidence and validation layer. The corpus is a reviewed source of practices, not a blanket endorsement of every deposited line and not a journal certification service.

## Required sequence

For a new project:

1. Inspect the target location read-only. Treat it as new only when it is empty or the user explicitly identifies a first build.
2. Decompose substantive work into readable state transitions. Merge retained-state handling, panel-key declaration, CPI transformation, dataset finalization, age/entity collapse, the `e(sample)` mean, estimation, `.ster` save, `.ster` load, Excel assembly, and figure assembly remain separately reviewable whenever present. Do not turn harmless setup, declared input loading, inspection, assertion, naming, logging, or one-statement bindings into ledger rows; use the direct-primitive boundary below. Resolve relevant checkpoints by bilingual aliases, exact normalized command anchors, and input/output state; do not search full code by vague substrings.
   For an end-to-end build or blind forward test, read [template-first-authoring.md](references/template-first-authoring.md). Maintain its atomic implementation ledger only when the user or evaluator requests a persistent template-reuse audit; otherwise keep planning evidence lightweight in the session.
3. For a Top 100 command explanation or example-coverage audit, call `inspect_top100_command_examples`; it returns all materially distinct guide blocks required by the command's complexity and keeps paper-code context separate from exact reusable support. For each substantive reusable authoring transition, including preparation and post-estimation, call `resolve_transition_evidence` first. Keep its guide-mechanics card and research-usage result as separate evidence: the guide is always non-writable and non-competing, and paper-occurrence support is never generation authority. Apply the complexity-weighted rule in [manual-first-policy.md](references/manual-first-policy.md): one bounded example may cover a simple command, while each material input, grammar, estimation, inference, returned-state, persistence, or handoff dimension of a complex command needs its own nonduplicate guide atom. An exact contract/version/facet with one guide mechanic returns that companion card; a material guide ambiguity returns no code and `selection_required`. At most one exact compatible, explicitly promoted audited usage row may become a template. Respect `split_required` for unrelated multi-command requests and `selection_required` for unresolved material choices. If no compatible usage template exists, use `search_labeled_checkpoints` and then the collected approved patterns only for diagnosis and a nearest nonbinding hint. Never mix unrelated commands in one `search_approved_patterns` call. Compare `unexpected_command_anchors`: a narrower span outranks a bundled one. If no suitable template remains, retain the guide card and pass the rank-relative nearest inspected usage candidate to fallback only as a nonbinding hint; it may still be absolutely distant or incompatible.
   For package coverage and canonical anchors, consult `data/package_command_catalog.json`. A newly encountered package belongs in the central command registry plus a state-compatible atomic template (or a declared reference-only family while its method contract is unresolved); it never justifies adding another estimator-specific detector branch.
4. Use `search_stata_manual` and `get_verified_stata_examples` only when the resolver's bounded guide card needs deeper syntax, returned-result, or command-state confirmation. Preserve the usage-template path: when exact compatible audited usage exists, select one complete variant and change only its permitted bindings. If no suitable usage template exists, or inspection, lint, runtime, or output evidence shows that the selection is wrong for the declared contract, follow [general-rule-fallback.md](references/general-rule-fallback.md) and write only the shortest readable transition supported by the retained guide mechanics. Inject the search-ranked nearest writable or reference usage candidate as a nonbinding hint, explicitly noting that rank-relative nearest may still be absolutely distant or incompatible. Borrow useful commands, ordering, state handling, or output idioms, or use none of it. Record `nearest_template_hint`, `fallback_trigger`, and `hint_used`; if no candidate exists, record the exact searched checkpoint and anchors. Do not require a claim that fallback code is better than the template. Ask the user when the remaining choice is substantive; neither guide nor fallback supplies it. In a source-isolated trial, keep the evidence boundary—no web, external connectors, prior answers, or evaluator assets—but allow local-manual-backed fallback code and harmless primitives.
5. Never promote a manual example to researcher-style evidence. If a substantive estimator, sample, comparison group, or reporting choice remains unresolved after the manual check, ask the user.
6. After the read-only inspection confirms a first build, call `workflow_blueprint` with `project_mode: new` and `new_project_confirmed: true` before writing code.
7. Present the pre-write proposal specified below and wait for explicit approval.
8. After approval, write direct, readable Stata code within the approved scope.
9. Call `lint_do_file` after creating or changing each do-file. For a newly created master do-file, pass `role: "master", authoring_state: "new"` so every direct `do` call is checked for its required role comment. Use `authoring_state: "modified"` for an existing master changed in the current task and `existing_audit` for read-only legacy inspection.
10. Fix every error and resolve or explicitly explain each warning.
11. After final code spans are frozen, apply `report_policy: required|optional|disabled` to the project-root `report.md`. A code-writing plan defaults to `required`, while a standalone read-only audit defaults to `optional`. Under `required`, create or update the report with one row for every selected template and every `general_rule_fallback` span; under `optional`, omission is allowed; under `disabled`, including an explicit no-report request, do not create or modify the target file. The legacy `require_report` option is a compatibility alias for `required` when no explicit report policy is supplied. Record the actual project-relative `.do` path, one-based inclusive lines, checkpoint, template `label_id` or fallback `-`, and reason. Every fallback reason uses `nearest_template_hint=<label_id|none>; fallback_trigger=<no_suitable_template|wrong_selection>; hint_used=<borrowed idea|none>`. Harmless primitives are not rows. With a required policy, call `audit_stata_project` using that policy; use `strict_structure: false` unless the user explicitly approved a new-project structure contract.
12. When execution is requested, run the approved entrypoint from a clean generated-results state and verify the concrete `.dta`, `.ster`, Excel, PDF, and log outputs named in the research contract. This is execution verification, not deployment or submission packaging.

For an existing project, call `plan_dictionary_repairs` with the project path and the user's exact request before proposing changes. It must inventory folders, files, entrypoints, call order, artifacts, estimate state, and code style; translate only the requested or defective work into dictionary headwords; and rank compatible variants. Call `audit_stata_project` with `strict_structure: false` when a wider integrity audit is needed. Preserve every compatible existing name and role, and search only for headwords in the intervention list. Do not create, rename, move, or split files merely to match the new-project template. Present the exact pre-write proposal and wait for explicit approval before changing anything. Lint each approved change and audit the project again.

When the requested file is a lightly adapted sibling of an existing canonical `.do` file, use `plan_dictionary_repairs.source_reuse` before dictionary fallback or fresh generation. Declare the canonical source, destination, and every permitted literal replacement, deletion, or insertion with its expected occurrence count. Use planner `scope.include_paths` or `scope.exclude_paths` to prune unrelated raw, result, archive, and bad-code trees before inventory. Copy the source without rewriting it, apply only those declared edits in order, and pass the finished candidate back as `candidate_path`; treat only `verified_exact` as a verified adaptation. Any other difference blocks the write. This contract is estimator-agnostic: do not add estimator names to detectors merely to preserve an existing source file.

## Pre-write approval gate

Read [readme-contract.md](references/readme-contract.md) for an approved new first build or overhaul. It is researcher documentation, not a distribution or submission contract.

Read-only inspection, search, lint, and audit may happen before approval. Before creating or modifying any project file or folder, show the user:

- folders to create
- files to create
- existing files to modify
- files to move or rename, normally none
- files to delete, normally none
- existing outputs that will be overwritten
- the entrypoint and execution command that will run after creation
- for an overhaul, one display-ready tree containing every approved creation, modification, move, rename, and deletion
- every new persistent analysis variable and its reader-facing description, source or exact formula, unit and observation level, creation file, period/geography, coding/missing rule, and use, or an explicit statement that there are none
- whether the project-root `README.md` will be created or amended to retain the approved tree and variable descriptions
- whether the project-root `report.md` will be created or amended under `report_policy: required`, omitted under `optional`, or protected from creation/modification under `disabled`

State explicitly that no project write or full execution will begin until the user approves this list. For an approved new first build or overhaul, retain the approved actual tree and persistent-variable descriptions in the root README as researcher documentation. Do not add a dependency inventory, installer, version table, packaging manifest, or deployment scaffold unless separately requested. If the plan changes materially after approval, stop and obtain approval for the revised list.

## Evidence rules

- Treat each labeled checkpoint as a small state-transition block. Match its `input_contract` and `selection_conditions`, choose one compatible variant, and preserve the code nearly verbatim while changing only `minimal_edit_fields` and `required_changes`.
- Keep multiple researcher variants in the same `variant_group` when their conditions or tradeoffs differ. Do not average, splice, or merge them by default. A `conditional_keep` block requires its listed conditions; a `drop` block is comparison-only and must never be copied.
- Give preprocessing and post-estimation blocks the same retrieval priority as regression blocks. Do not start from a long end-to-end script when shorter labeled load, audit, cleaning, integration, sample, treatment-timing, estimation, summary, assembly, and export blocks can be composed.
- Keep the stable English checkpoint ID separate from its Korean and English display names. During dictionary development, refresh and show `review/dictionary_toc.md` and `review/labeling_review.md` after every meaningful labeling batch; do not wait for the corpus to be complete. Preserve `review/review_queue.md` as the human-maintained priority list.
- Give every reusable non-negative label a source-evidenced `template_input_profile` and compare its six fields—data structure, record unit, required keys, source basis, time structure, and variable characteristics—with the current project before minimal editing. Keep the compact `input_signature` as supporting evidence. Include panel length or year/wave span, balance, frequency, units, and transformations only when the source establishes them; otherwise write `unknown`. Never fill these fields from variable names alone. Audit profile/signature completeness separately from package and label counts.
- Use `inspect_dictionary_coverage` when judging whether the corpus has actually covered a stage or package. Keep package review accounting separate from label count: only `end_to_end_read` proves every cataloged `.do` file was read, while reusable labels still require a safe atomic block and an adjudicated state contract. Do not infer that a zero-label package was skipped or that a many-label checkpoint is universally compatible.
- From `search_labeled_checkpoints`, copy only results with `auto_select_allowed: true` and quality `preferred_candidate` or `conditional_candidate`. From the `search_approved_patterns` fallback, copy only results with `approved_for_generation: true`.
- Never retrieve or copy a span whose `max_loop_depth` is 3 or greater. Prefer depth 0 or 1. A depth-2 span is eligible only after explicit review confirms two plain named lists or numeric ranges, one repeated mechanical body, substantial code reduction, and no hidden sample, estimand, specification, grouping, or output-placement choice. Unreviewed depth-2 spans remain contextual evidence only. Source files with loop depth 3 or greater and chunks that mention TeX output are excluded from the derived reference layer.
- Keep each example's package ID, DOI, file path, and line span when explaining its provenance.
- For canonical summary-statistics work, search `descriptives.summary_dataset`, `exports.descriptive_excel_sheet`, and `figures.descriptive_bar` before direct construction. The current AER/AEJ atoms cover grouped mean/count, tabstat count/mean/SD materialization, grouped percentiles, collapse-to-long structure, first versus additional Excel sheets, and grouped bars. Compose only the required producer-to-consumer atoms; formatting, mixed-stat assembly, or semantics absent from their source spans remain narrow fallback with closest-template evidence.
- Keep checkpoint ID, variant, source package/DOI, path, line span, source-file and source-block hashes, selection conditions, minimal edited fields, consuming project file, and one `substep_id` per atomic transition in session or audit evidence. Do not create a project `manifests/` folder or template-reuse manifest by default. Use `template_reuse_check` only when the user explicitly requests a persistent selection audit or an existing project already uses that contract.
- Write reader-facing do-file comments only for project-local state transitions: input meaning, a new variable's formula or definition, a retained merge or filter rule, the active sample or specification, and the purpose of an output. Do not put journal or repository names, template or source names, internal label/checkpoint/substep IDs, source paths, or provenance markers in generated comments. Keep those details in session or audit evidence. Preserve a source name in a comment only when that source is itself part of the project's data-acquisition contract.
- When a persistent template-reuse audit is requested, a native substep records its project-local target span and one of three contracts: project-specific formula, dictionary gap, or template-mismatch fallback. For a mismatch fallback, record the rank-relative nearest candidate as a hint, the `no_suitable_template` or `wrong_selection` trigger, and any hint used; do not infer compatibility from ranking or justify the fallback as superior. A compatible template remains preferred evidence; skipping it is advisory by default and becomes blocking only when the caller explicitly requests strict template-reuse enforcement.
- Do not create a primitive mode, label, ledger row, provenance record, `report.md` row, or `DIRECT FALLBACK` wrapper for harmless direct statements. Typical examples are `sysuse <built-in>, clear`, `use <declared input>, clear` without `if`/`in`, `version`, simple `set` commands, approved path/name bindings, `confirm`/`describe`/`codebook`/`count`/`assert` checks, `encode` of a declared identifier, `label variable`, plain `summarize` or `tabstat`, exact `estimates clear`, approved log open/close, and a requested `.gph` save of the active graph. These primitives never authorize dependency probing. If returned state later drives a substantive sample, estimand, transform, or reporting choice, review that larger transition normally. Merge retained states, sample restrictions, formulas, estimation, `e(sample)` means, estimate handoffs, figure/PDF assembly, axis decisions, and final dataset save should be checked against templates first, but no suitable template or a wrong selection leads to fallback with a rank-relative nonbinding hint rather than a forced stop.
- A master do-file may use one equally narrow prompt-only orchestration shell without a template, ledger row, provenance, or fallback marker when the caller has already approved the master-log path and the exact ordered do-file paths. Write one `log using`, the flat caller-declared sequence of direct `do` calls, and one `log close`; an exact caller-declared completion display may follow. Immediately above each individual `do` call, write one Korean comment sentence explaining that called file's project-local role, for example `* 원자료를 정리해 분석용 자료를 만든다.` Do not substitute a filename-only comment. Do not infer stages or order, add a loop, program, registry, dispatcher, conditional, positional string, dependency probe, captured stage failure, alternate path, or setup framework. Every called file must exist. This exception only exposes an already-declared execution order and cannot supply a research transition or rescue a missing template.
- For an unconditional `m:1` complete-match contract, select `merge.m1_complete_match_assert.v1` rather than shortening it to `keep(match)` or `nogen`. For a declared final analysis dataset, select `dataset.finalize_declared_inventory_order_sort_save.v1` for `keep`, `order`, `sort`, `compress`, and `save`; labels remain adjacent to variable creation.
- Treat `reference` results as method or structure context only.
- Request `negative` results only to explain anti-patterns. Never copy them into generated code.
- Never infer that an entire package is approved because one span is useful.
- Package-first expansion keeps `estpost`/`eststo`/`esttab`, `ivreg2`/`ivreghdfe`, and other distinct command families separately indexed. An indexed family is not automatically writable: respect its template policy, input contract, and evidence status. Templates may target Excel, PDF, or a required `.ster`; never install/probe a package, emit TeX, or reconstruct coefficients or standard errors manually. Quarantine manual result-to-table transfers instead of adapting them.

Keep the detailed atomic implementation ledger and source hashes in the active session or explicit template-reuse audit rather than duplicating them in the research project. When a code-writing plan uses the default required policy, root `report.md` is the smaller debugging record: actual target ranges, selected label IDs, fallback triggers, and hints used. Optional and disabled policies may omit it, and disabled must not touch an existing file. For corpus sources, retain `source_package_id` and `repository_doi`; for declared source snapshots, retain `source_kind`. Source and target spans are one-based inclusive. This is static evidence, not a substitute for an independent clean Stata run.
- Prefer several short, relevant spans over a whole do-file.
- Use exact command anchors and state contracts in `resolve_transition_evidence` first. Retain its guide card. Only when its route reports fallback, mismatch, or missing usage should the legacy labeled-block and selected research-practice corpus searches provide diagnostic evidence or a nearest nonbinding hint. Use deeper StataCorp manual search only to decide whether syntax and returned state are valid, and replication-safety rules to decide whether the workflow is portable and auditable.
- Do not call a lint-clean file passed. `static_clean` means only that deterministic guards found no issue. A syntax pass requires an official simple example and a successful Stata execution record.

## Workflow coverage

Do not reduce research code to regressions. Cover all applicable stages: import, integrity audit, cleaning and labels, merge and reshape, panel construction, descriptive statistics, balance and sample flow, estimation, robustness, figures, exports, and master orchestration.

Use a single project root. Keep raw inputs read-only and distinguish input, intermediate, analysis-ready, code/log, stored-estimate, table, and figure roles. For a first build with no existing compatible layout, use only the folder and entrypoint layout approved in the prompt or pre-write plan; common `do/`, `data/raw`, `data/generated`, `data/final`, `ster/`, `table/`, and `figures/` roles are not a forced template. Put `.gph` and exported `.pdf` files in the approved figure location. Do not create `work/`, `manifests/`, `output/`, or `logs/` folders by default. In an existing project, preserve its current folder names, paths, and valid entrypoint rather than imposing a default structure or inventing a second one.

## Labeled block composition

For final Excel file types, the direct no-program path must name an explicit `.xls` target. The canonical `outreg2_xlsx` formatter writes `.xlsx` and is available only when one workbook needs two or more sheets. Apply the same extension split to 2SLS first-stage and second-stage workbooks.

Think of the workflow as a chain of small contracts rather than one generated do-file. A block may be used only when the current data state satisfies its `input_contract`; after use, its `output_contract` becomes the state available to the next block. Respect `composition.can_follow`, `composition.can_precede`, and `composition.incompatible_with`.

For the same checkpoint, inspect returned variants together. A `variant_group` contains alternatives that perform the same transition: select one rather than splice them. Distinct sequential groups may be composed when their state contracts connect. A `canonical_default` is only a final tie-break after state compatibility; it never overrides an existing interface. If no variant genuinely matches, consult the approved corpus and official manual as needed, then enter fallback with the rank-relative nearest inspected candidate only as a hint. Ask the user only when the remaining choice is substantive.

Before treating a label as writable, check `quality_rubric_review`, scope, and explicit promotion record. Auto-select only an explicitly promoted `preferred_candidate` or `conditional_candidate`; keep `reference_only` as evidence and gap diagnosis, not writable code. Legacy implicit autos, generated guide cards, and generated paper-occurrence support all have `auto_selectable=false`. Promotion requires runtime pass, selector-positive pass, and sibling-negative pass in addition to the source, hash, context, and external-evidence review. Prefer `reuse_scope: general`; use `method_specific` only when the target estimator, profile, data shape, and identifying choices match. A known profile/signature mismatch blocks automatic reuse, while an `unknown` field requires inspection rather than a guessed match. Explicit method/state words in the request hard-gate a generic alternative before ranking. Do not return `project_specific` blocks in default generation, even when indexed. The multi-sheet final Excel formatter is the only current explicit canonical exception. Concrete variable names, keys, file names, and data shape are expected bindings when isolated in `minimal_edit_fields`; distinguish them from hidden sentinel rules, author-only helpers/globals, scattered edits, or research choices embedded in control flow. A newly found corpus span must pass the source/hash/context and external-evidence rubric review before labeling and reuse.

The final Excel assembly has one output contract and two implementation scales. Treat the raw `outreg2` table as complete: do not improve, filter, relabel, reconstruct, or selectively keep its model headers, dependent-variable headers, coefficient rows, standard-error rows, omitted/base rows, or notes. A workbook with one sheet uses direct visible `outreg2 replace/append` statements without a program, regardless of outcome or specification count. Use the canonical `outreg2_xlsx` formatter only when one workbook requires two or more sheets. Both paths may add adjusted R-squared and the dependent-variable mean as the only two extra statistic rows. Compute each mean on `e(sample)` or an exactly equivalent saved estimation sample. In a direct one-sheet flow, run `quietly summarize <depvar> if e(sample), meanonly`, bind `r(mean)` to a local, then use `adjr2 addstat(Dep. variable mean, <that local>)`; no other `addstat()`, `addtext()`, `e()`, `keep()`, `drop()`, or row relabeling is allowed. Keep that calculation and `outreg2` call beside the active model; do not add a global for one literal path, store and restore a single active estimate, define a one-use program, or import and re-export a scratch table merely for generic formatting. In a multi-sheet flow, the caller stores current approved results or restores durable `.ster` states under readable in-memory estimate names and passes those names in output-column order; the formatter does not assume an outcome count, specification count, sample, estimator, or model role. Before choosing either path, build an output-flow profile from the full project: outcome meaning/label, definition and measurement relationship, unit and transform, sample and estimand, estimate handoff, and specification order. Define each reader-facing semantic `sheet_group` once from evidence about which outcomes a reader should compare together; no one metadata field must match, and similar names are not evidence. Set `decision_source` to `user`, `existing_project`, `model_from_metadata`, or `caller_declared` and retain the supporting `grouping_evidence`; the tool also normalizes its documented aliases. An object wrapper with `source`, `type`, or `kind` is accepted and normalized by the same contract. Record workbook, sheet, and sample separately in `sheet_plan`.

For 2SLS, preserve the same sheet-cardinality rule instead of inventing an IV table system. A one-sheet first-stage or second-stage workbook uses direct `outreg2 replace/append`; use the formatter only when that workbook needs two or more sheets. Save or restore each first-stage estimate through the estimator's native returned-state interface when a later placement requires it, attach its own `e(sample)` dependent-variable mean, and treat first-stage results as an explicitly named model-role group in the same output flow. First-stage and second-stage columns use the same raw `outreg2` source and may add only adjusted R-squared when defined and the dependent-variable mean. Do not add first-stage F statistics, weak-instrument diagnostics, custom coefficient filters, or renamed rows; keep any requested diagnostic testing in the estimation or audit flow. Treat `.ster` replace/seed, append, numbered load, in-memory store, and restore as separate state transitions rather than one generic persistence block.

Plan event-study axes independently from Excel sheets. Exactly one outcome uses the direct no-loop `axis_mode: automatic` template. For two or more outcomes, use one flat outcome loop. Declare `axis_mode: fixed_group` only for genuinely close, directly comparable outcomes under the same specification and sample comparison and with the same coefficient unit and transformation. Each fixed group must record the outcome membership evidence and the basis for its numeric minimum, maximum, and step; voluntary and involuntary unemployment rates are an example when these conditions hold. Use `axis_mode: automatic` for every other plot. When exactly one fixed group and one or more automatic outcomes share the rest of the figure interface, select the complete mixed-axis flat-loop variant: declare the full outcome list and fixed subset once, reset one axis-options local on every iteration, and use one visible membership `if`. This is the only axis-policy branch allowed inside that loop; multiple fixed groups or any second per-outcome choice require reselection rather than extending it. An `axis_group` is usually finer than a `sheet_group`, may cross sheet boundaries when the evidence supports it, and must never inherit a fixed range merely from sheet membership. In the selected event-figure variant, place the comparison/sample legend below the axis, put the raw outcome variable name alone at the top, and export the PDF immediately before the loop closes when a loop is present. Do not create a graph-job registry or a second loop.

Use the labeled reshape, `tsfill`, named `graph combine`, and collapse-with-label-round-trip blocks when their input profiles match. Use a named sample-flow `postfile` only when the researcher provides the checkpoint meanings and their order; it must declare typed rows, post the named counts, and `postclose` the dataset without disturbing the active data. It is never a bridge for coefficient or table reconstruction.

Preserve Stata factor-variable coefficient identity across estimation and reporting. Do not manually generate `treat_y2015`, `_y2015`, or similar treatment-by-year dummy variables as substitutes for a factor-variable interaction, even when no `rename` command is used. For a conventional event-study RHS with a declared window, write one flat native term per nonreference level, such as `2015bn.time#1.treatment 2016bn.time#1.treatment`: leave the declared design reference absent, use one `#`, and do not use plain `i(<numlist>)`, `ibn(<numlist>)`, or another base marker. This event-RHS rule does not prohibit a separately justified heterogeneous slope such as `year##c.baseline_control` inside `absorb()`. Do not rename native coefficient tokens. Runtime verification must find every declared nonreference level in `e(b)` under the exact raw token Stata returns, including a retained `bn` marker on the first no-base term or an estimator-created `o` marker. Event-study `keep()` targets those raw names; display `order()` must additionally retain exactly one blank slot for the omitted reference period, with an explicit x-label map, reference-point position, and policy boundary derived from that slot. Display labels may simplify presentation without replacing coefficient identity. All event-study graph text is English. For other graphs that contain Korean text, set the graph font to `Malgun Gothic`.

## Scope, intent, and validation status

`audit_stata_project` defaults to the active reachable workflow: resolve `scope.entrypoints` or the selected top-level master, traverse its reachable call graph, and use project-level producer-consumer edges for the requested stages. Explicit `scope.mode: all` audits the whole tree; project-relative `scope.include_paths`/`scope.exclude_paths` provide a bounded alternative, with excluded directories pruned before discovery limits and call-graph construction. Unreachable files are listed as inactive advisories without full lint and do not block the active workflow unless explicitly included. Multiple plausible top-level masters produce `needs_review` without an arbitrary active workflow until `scope.entrypoints` is explicit. This is a general scope contract, not a project-specific exception.

Classify intent before selecting a headword. Korean and English review-only/no-change signals—검사, 점검, 평가, 진단, 검토, 발전 가능성, 수정하지 않는다, `review`, `audit`, `inspect`, `assess`, `diagnose`, `explain`, and `do not modify`—take precedence over incidental “add,” “improve,” or “feature” words. They set `code_required: false` and `write_authorization.status: not_requested`, so no writable template or project write may be planned. Only an explicit, non-contradicted write request can authorize code.

Master role checks use `authoring_state`: missing role prose is an error for a new master, a warning for a modified master, and not a retroactive block for an existing master under audit. With `report_policy: required` (including the legacy alias `require_report: true`), check only caller-authored substantive `authored_spans` with confident boundaries; each needs one contiguous row and a valid one-based range. Harmless primitives, research-code provenance markers, and untouched legacy files are not implicit coverage requirements.

Multi-sheet and estimate multiplicity must be inferred from execution-ordered project-level producer-consumer evidence using call-time macro values. Producer, durable-estimate, macro, workbook, and sheet state is isolated across disconnected workflow components. A later producer or a durable `.ster` file does not satisfy an earlier in-memory consumer. Dynamic/runtime-only names are `context_pending` and nonblocking until resolved; per-file lint cannot block merely because it lacks project topology. Keep `runtime_success`, `static_audit`, and `substantive_validity` as independent statuses. A missing main log leaves runtime `not_checked`. Static estimability checks cover only certain structural risks; exact omitted/collinear terms require runtime `e(b)` readback with a nonempty declared nonreference contract, and estimand interpretation remains a substantive judgment.

Mark derived canonical/template material `independent_support=false` and exclude it from independent external-evidence counts. It remains lineage evidence but cannot count as independent support. Deposited external packages remain a separate evidence class. The tool does not perform target-relative package-lineage comparison, so their `independent_support` flag is not proof of different target lineage.

`loop_depth` counts active executable loop nesting. `structural_depth` counts nested executable/control blocks, including conditionals, loops, and program blocks. `loop_depth >= 3` is blocking; `structural_depth >= 4` is a review warning. Never report one measure as the other.

## Template mismatch and fallback

Read and apply [general-rule-fallback.md](references/general-rule-fallback.md) before writing any non-template substantive transition. Fallback implements only an already-decided atomic contract; it never supplies a missing research or output choice.

After selecting a block, compare its input state, output state, control flow, and required interface with the target. Iteration is allowed, and the number of drafts is not a failure criterion. Revise only from concrete lint, runtime, or output evidence. When the block is compatible and the failure is confined to a declared binding or `minimal_edit_fields`, delete the affected rendered span and cleanly render that atomic substep again from the selected block; do not patch already modified generated code. If its frame, algorithm, control flow, interface, or output contract would need to change, discard that span, search again with the observed mismatch, and select another complete variant. Never keep patching the first choice or splice two variants into a third implementation.

When a substantive transition has no genuinely close template, or the selected template is wrong for the observed state or declared contract, GPT must leave template mode and use the general-rule fallback. Pass the search-ranked nearest inspected candidate into fallback as a nonbinding hint and state that nearest does not establish suitability. Do not add provenance or fallback markers to the research code. After final line numbers are stable, record the actual contiguous target range, `no_suitable_template` or `wrong_selection` trigger, and any hint used in root `report.md`.

Fallback is not a second template system. Write the shortest readable statements for the current state transition and keep indentation shallow. Use the injected candidate only for helpful commands, ordering, state handling, or output idioms; do not preserve a structure that caused the mismatch. Prefer one flat loop. A two-level loop is allowed only when two plain named lists or numeric ranges repeat the same mechanical body, removing a substantial amount of duplication while leaving sample, estimand, specification, grouping, and output placement visible at the loop site. Loop depth 3 is forbidden. Do not create positional job strings, registries, dispatchers, one-use programs, unused or future-facing options, generic caller interfaces, unnecessary intermediate variables, manual event dummies, coefficient reconstruction, or project-specific framework rules. Lint the transition immediately. A later compatible template is evidence to reconsider the fallback, not a demand to retain the earlier wrong selection.

Before final execution or independent evaluation, clean the authored source rather than preserving its revision history. Each substantive transition must have exactly one final implementation path: one selected template, one harmless direct statement, or one concise general-rule fallback. Remove every superseded variant, compatibility wrapper, duplicate calculation, dead branch, unused macro, option or temporary variable, commented-out alternative, and stale fallback marker. Verify that every master `do` target exists and every declared completion token has one reachable callee producer. A canonical block rejected by the linter is a plugin defect to report and fix in a plugin-owned fixture. Freeze after final lint, project audit, fresh runtime, exact-output, and rendered-readability checks; require template-reuse evidence only when that audit was explicitly requested.

## Partial repair and overhaul

Default to partial repair. Scan the codebase, user-authored files, call graph, existing outputs, estimate handoffs, and visible style before selecting a block. Mark stages outside the user's requested headwords as `preserve`. Add a preceding state transition to the intervention list only when static or runtime evidence shows the requested block cannot consume the current state; report that evidence instead of silently widening scope. A caller-supplied `overhaul` flag cannot widen a narrow natural-language request: accept overhaul only when the user explicitly asks for it or the planner records concrete interface incompatibility evidence.

Before dictionary retrieval, decide whether the request requires code. A review, audit, diagnosis, or explanation-only request loads no writable template, and the absence of a write signal should remain read-only. When code is required, classify its scale by the number of necessary state transitions, not by projected line count: `atomic_substep` for one exact Stata command or one explicit substep, `checkpoint` for one workflow headword, `multi_checkpoint` for several named transitions, and `overhaul` only when explicitly requested or proven unavoidable. Convert that bounded footprint into scale keywords plus checkpoint IDs and exact command/state anchors. Evaluate dictionary metadata as needed, but load code for only one compatible variant per selected headword and never load writable code from an unselected headword. Alternative methods may remain as limited metadata so compatibility can be checked without importing their code.

Classify the user's intent before planning writes:

- `add_feature`: when the user asks for a new capability without explicitly asking to edit their existing code, map the existing workflow to completed dictionary headwords and freeze the completed prefix. Read frozen code only to fingerprint its outputs and calling convention. Add the requested downstream block without rewriting the producer's computational content.
- `modify_existing`: when the user explicitly asks to fix or change their code, map the named target to one or more dictionary headwords. Only the explicit target files or locations are mutable; every other headword and file is frozen.
- `overhaul`: use only when explicitly requested or when a reported incompatibility makes the target impossible under the current interfaces.

For example, an Excel-only request over an existing preparation and regression pipeline maps only to `final_excel_assembly`. If every target workbook has one sheet, restore each required durable `.ster` state only when needed and call visible `outreg2 replace/append` directly; do not define a formatter. If one workbook has two or more sheets, restore approved states under readable names and use `outreg2_xlsx` for those placements. Never rewrite preprocessing or estimation merely to make reporting easier.

Support overhaul only when the user explicitly requests it or the current workflow cannot satisfy the target and the incompatibility is demonstrated. Even during overhaul, decompose the work into dictionary headwords and select one state-compatible variant per headword rather than generating a new monolithic workflow. Pass the proposed paths and planned variables to `plan_dictionary_repairs`, then show `overhaul_prewrite_proposal.tree_markdown`, the planned-variable table, and the root README action before any write. For an existing project, this tree contains only approved changes and never imports the new-project tree automatically.

After selecting a variant, preserve its control flow. Allowed edits are limited to its `minimal_edit_fields`, `required_changes`, and necessary input/output bindings. If the block's frame or algorithm must change, stop adapting it and select or label a different variant.

Fingerprint integration interfaces before any edit: existing input commands, output commands and paths, master call sites and order, public macro names used across do-files, program names and `syntax`, estimate handoff form, workbook and sheet names, and any declared estimate ordering. Preserve those interfaces by default. A private macro or a global with only one consuming do-file is classification evidence, not automatically a public interface; localize it when the writing contract below calls for reader-visible scope. Integration may add a new owned output, bind a selected block to an existing output without renaming it, or insert one explicit direct call at a verified producer boundary when approval permits. It may not rename or overwrite existing interfaces, change caller arguments, reorder current calls, replace the estimate handoff to fit a preferred example, or invent an unlabeled glue program. If the selected variant cannot consume the fingerprinted interface, report the mismatch and select or label another variant.

## Research execution validation

The plugin does not prepare distribution packages or manage dependencies. When the user asks for an executable research workflow, lint every authored do-file, apply the selected `report_policy` (the code-writing planner defaults to `required`) to root `report.md`, audit the requested stages with that policy, run the approved entrypoint in a clean generated-results state, check the log for Stata errors, and verify the exact outputs named in the research contract. A standalone read-only audit defaults to `optional`. An explicit no-report request sets `report_policy: disabled` and the plugin must not create or modify `report.md`; `require_report` remains a compatibility alias for `required`. Preserve source and baseline outputs. A root README may retain the researcher-facing folder tree and variable descriptions; do not add repository deployment metadata, installation code, a dependency record, or a submission checklist as a side effect of validation.

Read [manual-first-policy.md](references/manual-first-policy.md) when the fallback chain reaches syntax or returned-state validation. Read [general-rule-fallback.md](references/general-rule-fallback.md) before writing any non-template substantive transition. Read [quality-policy.md](references/quality-policy.md) before adjudicating findings. ## Stata writing contract

- State outcome, treatment, controls, sample, fixed effects, and clustering near each specification.
- Reserve `global` for an intentional cross-do-file contract. Setup may define shared directory roots such as project, data, table, figures, and ster. A leaf input or output filename such as `summary_excel = $table/file.xlsx` belongs in the one child do-file that consumes it: declare it as a `local` near first use, or use the literal directly when it appears once and is clearer. Keep a leaf filename global only when two or more do-files intentionally share that exact producer-consumer artifact contract. Put repeated regression-specific controls, sample conditions, event-study RHS terms, fixed effects, and clustering definitions in `local` macros in the consuming estimation do-file, adjacent to the specifications that use them; keep a one-use list explicit in the command when that is clearer. Do not hoist these bindings into setup or fan them out into per-outcome globals.
- Put same-file event selectors, coefficient order, axis labels, reference position, and graph notes in `local` macros near the graph command. Use a literal instead when the value is used only once and the literal is clearer.
- Format long variable, outcome, estimate, coefficient, and option lists as meaningfully grouped multiline blocks. Use whitespace to align comparable entries and make group boundaries visible; keep short lists on one line. Do not align or reflow quoted labels, paths, notes, or other text where whitespace is data.
- Use `///` only when the immediately following physical line continues the same command, and indent every continuation line beyond the command's starting indentation. The final option or physical line has no `///`; never leave a blank line, comment-only line, closing brace, `end`, or a new command after `///`.
- Verify merge key cardinality before merging. Declare the retained merge states with `merge`'s official `keep()` option, or inspect and assert `_merge` before dropping it.
- Use `isid`, duplicate checks, missing checks, range checks, and stage-by-stage observation counts.
- Define each new variable near its creation and label new variables before saving a `.dta`.
- Record sample flow from raw input to every reported table and figure.
- Record named counts after every consequential restriction and retained-state merge; a start/end-only sample-flow file is incomplete.
- For grouped summary statistics, save mean, standard deviation, and nonmissing N in one named canonical summary dataset. Derive the table and figure from that same file instead of rebuilding the groups twice.
- Put `set seed` next to resampling code.
- Export final regression tables to Excel with the fixed canonical `outreg2` assembly contract above, figures to PDF, and estimates to `.ster` only when durable reusable estimation results are needed. Do not generate, retrieve, or recommend TeX output code.
- Keep factor-variable interaction coefficient names raw in Excel and event-study selectors. Never create manual `treat_yYYYY`/`_yYYYY` substitutes. Conventional event-study treatment-time terms use one flat `<level>bn.time#1.treatment` term for each nonreference level, verify every declared term in `e(b)`, and never use plain `i(<numlist>)`, `ibn(<numlist>)`, another base marker, or `##`; event-study graph text is English, while non-event graphs with Korean text use `Malgun Gothic`.
- Give paper-facing summary workbooks informative decimals for means, standard deviations, standard errors, and confidence intervals while keeping counts integral. Verify every required arbitrary JSON file with a real JSON parser before readiness; existence and hashes do not prove valid JSON.
- Use at most two active loop levels. Prefer a directly inspectable sequential block or one flat loop over a plain declared list. Use depth 2 only when the same mechanical block repeats over two plain named lists or numeric ranges and the duplication removed is substantial; keep every sample, outcome family, specification, group, and output placement legible at the loop site. Depth 3 is a blocking error. Never serialize research choices into positional job strings and recover them with downstream `word` parsing; do not hide nesting or dispatch in a helper. Prefer direct preprocessing do-file modules. A `program` is allowed only when a direct module cannot provide a required interface and its necessity, narrow scope, and input/output contract are recorded.
- At every implementation substep, write only the readable statements required by the current observed input-to-output contract. Do not design for future expansion. Do not add unused options, hypothetical branches, one-item loops, one-use programs, registries, dispatchers, or generic caller interfaces. This rule removes unneeded behavior; it does not compress necessary specifications or checks.
- Do not put installation commands in the research run, use `merge m:m`, force-drop duplicates, or manually bridge coefficients into tables. Keep research specifications directly inspectable; a final-Excel helper may only package already formatted `outreg2` output when workbook/sheet placement requires it.

Do not add setup metadata, version tables, installation instructions, dependency inventories, or installed-command probes to the research project. Run the user's requested estimator directly and do not silently replace it.
